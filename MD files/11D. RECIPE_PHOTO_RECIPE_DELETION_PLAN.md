# Plan 3D - Stergerea fotografiilor impreuna cu reteta

## Scop

Coordoneaza fisierele foto atunci cand este stearsa o reteta intreaga prin `RecipeLibraryService`.

Metadata este eliminata de `ON DELETE CASCADE`. Acest plan gestioneaza numai pregatirea, restaurarea si stergerea fisierelor locale.

## Dependinte

- planul 2 complet, inclusiv `ON DELETE CASCADE`;
- planul 3B complet pentru carantina;
- planul 3C complet pentru implementarea care va coordona fisierele.

## In afara scopului

- stergerea unei singure fotografii;
- reconcilierea dupa restart;
- modificari de schema;
- factory-uri;
- Web, App si ZIP.

## Regula de lucru

Executa un singur pas, explica fiecare modificare de comportament, nu rula build sau teste, indica verificarea utilizatorului si asteapta aprobarea explicita.

## Politica aprobata pentru erori

### Fisier deja lipsa

- nu blocheaza stergerea retetei;
- restul lotului continua;
- situatia este scrisa ca warning;
- metadata dispare prin cascada DB.

### Eroare inainte de stergerea DB

- fisierele deja mutate sunt restaurate;
- reteta nu este stearsa;
- operatia intoarce esec prin `RecipeSaveResult`;
- erorile de pregatire si restaurare sunt logate.

### Eroare la stergerea DB

- intregul lot este restaurat;
- operatia intoarce esec controlat;
- eroarea DB si eventualele erori de restaurare sunt logate.

### Eroare de cleanup dupa succesul DB

- reteta ramane raportata ca stearsa cu succes;
- eroarea este warning, nu esec al operatiei deja finalizate;
- continutul ramas in carantina este lasat reconcilerului;
- nu se adauga un tip nou de rezultat in `RecipeSaveResult`.

## Pasul 1 - Creeaza contractul coordonatorului si tokenul lotului

Fisiere noi:

- `CarteDeBucate.Core/Services/Photos/IRecipePhotoDeletionCoordinator.cs`;
- tipul opac intern pentru lotul pregatit.

Contractul permite:

- pregatirea in carantina a tuturor fisierelor unei retete din contextul curent;
- confirmarea stergerii dupa succesul repository-ului de retete;
- restaurarea lotului daca stergerea retetei esueaza.

Tokenul lotului:

- este opac;
- nu expune path-uri;
- nu este returnat catre Web sau App;
- pastreaza numai informatia interna necesara restaurarii sau confirmarii.

Nu implementa inca integrarea in `RecipeLibraryService`.

Verificare pentru utilizator: ruleaza build-ul Core.

Opreste-te si asteapta aprobarea.

## Pasul 2 - Implementeaza coordonarea lotului in RecipePhotoService

`RecipePhotoService` implementeaza separat `IRecipePhotoDeletionCoordinator`.

Pregatirea lotului:

1. verifica reteta in contextul curent;
2. listeaza metadata prin metoda repository potrivita;
3. muta fiecare fisier existent in carantina;
4. continua si logheaza daca un fisier lipseste;
5. daca alta mutare esueaza, restaureaza elementele deja mutate;
6. intoarce un lot numai dupa pregatirea completa.

Confirmarea lotului sterge definitiv continutul din carantina. Restaurarea lotului incearca toate elementele chiar daca unul esueaza.

Adauga teste pentru:

- lot gol;
- un singur fisier;
- mai multe fisiere;
- fisier lipsa;
- esec la mijlocul pregatirii;
- restaurarea elementelor deja mutate;
- confirmare;
- eroare partiala la confirmare;
- eroare partiala la restaurare.

Verificare pentru utilizator: ruleaza numai testele coordonatorului.

Opreste-te si asteapta aprobarea.

## Pasul 3 - Integreaza coordonatorul in RecipeLibraryService

Modifica:

- `CarteDeBucate.Core/Services/Library/RecipeLibraryService.cs`;
- `CarteDeBucate.Tests/Services/RecipeLibraryServiceTests.cs`.

Pastreaza constructorii existenti compatibili si adauga o cale optionala pentru `IRecipePhotoDeletionCoordinator`.

Cand coordinatorul exista, `DeleteRecipe`:

1. aplica validarea si regulile existente;
2. pregateste lotul foto;
3. daca pregatirea esueaza, nu apeleaza stergerea repository-ului;
4. sterge reteta prin metoda potrivita contextului;
5. lasa cascada DB sa elimine metadata;
6. confirma lotul dupa succesul DB;
7. restaureaza lotul daca repository-ul arunca;
8. raporteaza succes si logheaza warning daca numai confirmarea finala esueaza.

Cand coordinatorul lipseste, comportamentul ramane identic cu cel actual. Aceasta regula pastreaza compatibilitatea si modul JSON.

Nu modifica Web sau App.

Adauga teste pentru:

- comportamentul existent fara coordinator;
- pregatire reusita;
- pregatire esuata;
- stergere DB esuata si restaurare;
- stergere DB reusita si confirmare;
- confirmare esuata dupa succesul DB;
- context autentificat;
- modul global.

Verificare pentru utilizator: ruleaza `RecipeLibraryServiceTests`.

Opreste-te si asteapta aprobarea.

## Pasul 4 - Verificarea finala a planului 3D

Agentul nu ruleaza teste sau build.

Cere utilizatorului sa ruleze testele coordonatorului si `RecipeLibraryServiceTests`.

Confirma explicit:

- fisierul lipsa nu blocheaza stergerea;
- erorile anterioare DB opresc stergerea;
- erorile DB restaureaza lotul;
- cleanup-ul esuat dupa DB nu transforma succesul in esec;
- constructorii existenti raman compatibili;
- comportamentul fara coordinator ramane neschimbat;
- Web si App nu au fost modificate.

Opreste-te si asteapta aprobarea finala.

## Definitia de finalizare

Planul 3D este finalizat cand stergerea unei retete coordoneaza sigur fisierele locale, pastreaza compatibilitatea existenta si toate verificarile au fost confirmate de utilizator.
