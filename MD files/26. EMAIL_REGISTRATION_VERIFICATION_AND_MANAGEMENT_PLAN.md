# Email Registration, Verification, and Account Email Management Plan

## 1. Outcome and scope

Replace username authentication with email-only authentication and require email verification for every newly registered account.

Existing database users will be converted once through a manually executed migration tool. The tool will preserve user IDs and related data, assign an email address to each user, mark the email as verified, and replace the password hash using the former username as the temporary password.

There will be no permanent legacy-account state, nullable username, account-type flag, or parallel username login path. After conversion, existing and new users follow the same email-based authentication rules.

The console application has been archived under `archive/CarteDeBucate.App` and removed from `CarteDeBucate.slnx`. It is therefore outside the scope of this feature. Console prompts, console registration, and archived console data do not need to remain compatible.

Some console-era JSON authentication code still exists in the active Core project. Because removing `User.Username` would otherwise force that unused code to be maintained, this plan removes the remaining JSON user authentication path from Core as part of the identity migration.

This is an implementation plan only. It does not authorize schema or application changes yet.

## 2. Current architecture and important findings

### Authentication

- Authentication is custom and does not use ASP.NET Core Identity.
- `CarteDeBucate.Core/Services/Authentication/AuthenticatinService.cs` currently performs username registration and login.
- Successful registration currently authenticates the user immediately.
- `CarteDeBucate.Web/Controllers/AccountController.cs` creates the MVC authentication cookie.
- MVC uses cookie authentication.
- The Chrome extension does not submit a password directly to an API. An authenticated MVC session creates a short-lived extension authentication code, which is exchanged for a JWT through `AuthenticationApiController`.
- JWTs currently contain the user ID and username.
- The extension runtime only needs a valid current-user object; changing the response property from `username` to `email` mainly affects tests and the API contract.

### Password hashing

- `AuthenticationService` currently uses PBKDF2-SHA256, a 16-byte random salt, a 32-byte hash, and 100,000 iterations.
- A separate, apparently unused `PasswordHasher` uses only 10,000 iterations.
- These implementations must be consolidated before the migration tool or new registration flow uses them.

### Persistence and migrations

- SQLite access uses `Microsoft.Data.Sqlite` and enables foreign-key enforcement through `SqliteConnectionStringFactory`.
- Migrations are hand-written in `DatabaseScripts` and applied transactionally by `DatabaseMigrator`.
- `DatabaseInitializer` creates current table definitions before migrations run.
- The active web database currently contains 12 users and 234 recipes associated with users.
- A second database at the repository root currently contains no users or assigned recipes.
- The migration tool must require an explicit database path so it cannot accidentally modify the wrong database.

### Localization and configuration

- ASP.NET Core localization is already registered.
- The active request localization configuration currently supports only `ro-RO`.
- The Web project already has a .NET User Secrets ID.
- Existing secrets such as the JWT signing key are loaded through ASP.NET Core configuration.

### Archived-console remnants

The following active Core components are no longer needed after the console application was archived:

- `JsonUserRepository`;
- `AppSettings.UsersFilePath`;
- the storage-mode-based `CreateUserRepository` factory method;
- tests that exist only for JSON user authentication or `UsersFilePath`.

Database recipe storage and JSON recipe backup/import are unrelated and must remain unchanged.

## 3. Design decisions

### 3.1 Email is the only identity field

- Remove `Username` from `User`, the database, repositories, view models, claims, authentication codes, API responses, and active tests.
- Add required `Email`.
- Add nullable `EmailVerifiedAtUtc`.
- A user may authenticate only when `EmailVerifiedAtUtc` is non-null.
- Do not infer special privileges from a null email or another user-controlled value.
- Do not introduce `IsLegacyUser`, `AccountType`, or a permanent legacy login branch.

### 3.2 Existing users become normal verified users

The one-time migration tool will:

- preserve `Users.Id`;
- preserve `CreatedAt`;
- preserve all `Recipes.UserId` relationships;
- accept an explicit old-username-to-email mapping;
- normalize and validate each supplied email;
- set `EmailVerifiedAtUtc` to the UTC conversion time;
- generate a new salt and hash the former username as the password;
- omit the old username from the final schema.

Using a former username as a password is deliberately a temporary compatibility shortcut and is weaker than a normal password. The application should not be publicly accessible during conversion, the mapping must not be committed, and the converted credentials should be changed before they are relied on in a public deployment.

### 3.3 Password hashing remains custom for now

- Keep PBKDF2-SHA256 and the existing 100,000-iteration format for this feature.
- Consolidate hashing and verification into one password hasher used by login, registration, current-password verification, and the manual migration tool.
- Compare hashes using `CryptographicOperations.FixedTimeEquals`.
- Require a stronger password for new registrations, with 12 characters as the recommended initial minimum.
- Do not enforce the new registration rule during login for converted users.
- Do not introduce ASP.NET Core Identity as part of this work.

## 4. Proposed database schema

### 4.1 `Users`

```sql
CREATE TABLE Users (
    Id INTEGER PRIMARY KEY AUTOINCREMENT,
    Email TEXT NOT NULL COLLATE NOCASE,
    PasswordHash TEXT NOT NULL,
    PasswordSalt TEXT NOT NULL,
    CreatedAt TEXT NOT NULL,
    EmailVerifiedAtUtc TEXT NULL,
    PreferredCulture TEXT NULL
);

CREATE UNIQUE INDEX IX_Users_Email_NoCase
    ON Users (Email COLLATE NOCASE);
```

Rules:

- Normalize emails by trimming and lowercasing invariant before persistence and lookup.
- Limit email input to 254 characters.
- Treat `EmailVerifiedAtUtc IS NULL` as unverified.
- Store `EmailVerifiedAtUtc` as a UTC ISO-8601 string using the round-trip `"O"` format.
- SQLite has no dedicated date/time storage type; using ISO-8601 `TEXT` follows the repository's existing timestamp convention and sorts correctly when formatting is consistent.
- Store `PreferredCulture` as null when browser preference applies, or as a supported value such as `en-US` or `ro-RO`.

### 4.2 `UserEmailTokens`

```sql
CREATE TABLE UserEmailTokens (
    Id INTEGER PRIMARY KEY AUTOINCREMENT,
    UserId INTEGER NOT NULL,
    Purpose INTEGER NOT NULL,
    TokenHash BLOB NOT NULL,
    TargetEmail TEXT NOT NULL COLLATE NOCASE,
    Culture TEXT NOT NULL,
    CreatedAtUtc TEXT NOT NULL,
    ExpiresAtUtc TEXT NOT NULL,
    UsedAtUtc TEXT NULL,
    RevokedAtUtc TEXT NULL,
    FOREIGN KEY (UserId) REFERENCES Users(Id) ON DELETE CASCADE,
    CHECK (Purpose IN (1, 2)),
    CHECK (length(TokenHash) = 32)
);

CREATE UNIQUE INDEX IX_UserEmailTokens_TokenHash
    ON UserEmailTokens (TokenHash);

CREATE UNIQUE INDEX IX_UserEmailTokens_ActivePurpose
    ON UserEmailTokens (UserId, Purpose)
    WHERE UsedAtUtc IS NULL AND RevokedAtUtc IS NULL;

CREATE INDEX IX_UserEmailTokens_UserPurposeExpiry
    ON UserEmailTokens (UserId, Purpose, ExpiresAtUtc);
```

Token purposes:

1. Registration email verification.
2. Email-address change verification.

`BLOB` means Binary Large Object. `TokenHash` stores the raw 32 bytes produced by SHA-256 rather than a hexadecimal or Base64 text representation. It is slightly smaller than text and accurately represents the value as binary data. Encoding the same hash consistently as text would also be secure; `BLOB` is a representation and storage choice, not an additional security mechanism.

Do not make `TargetEmail` unique in the token table. The final `Users.Email` unique index decides ownership during atomic confirmation. This avoids allowing an unconfirmed request to reserve an email address indefinitely.

## 5. Token lifecycle

- Generate 32 random bytes with `RandomNumberGenerator.GetBytes(32)`.
- Encode the raw token with Base64URL for the email link.
- Hash the raw token with SHA-256.
- Store only the 32-byte hash.
- Set expiration to exactly 24 hours after issuance using `TimeProvider.GetUtcNow()`.
- Query by hash and purpose.
- Reject tokens that are expired, used, revoked, have the wrong purpose, or do not match the expected user and target email.
- Mark a successfully consumed token with `UsedAtUtc` in the same transaction that verifies or changes the email.
- Revoke outstanding sibling tokens when issuing a replacement or completing an operation.
- Opportunistically remove used, revoked, or expired tokens older than 30 days during token issuance or another small maintenance operation.

A fixed-length SHA-256 hash can be used as the database lookup value. No plaintext or reversible token is stored.

## 6. Migration strategy

### 6.1 Fresh and empty databases

Add two migration versions:

1. Replace the old empty username-based `Users` schema with the final email-based schema.
2. Create `UserEmailTokens` and its indexes.

Also update `DatabaseScripts.CreateUsersTable` and `CreateTables` so a brand-new database is created directly in the final state.

The old username column may have an inline uniqueness constraint and index. SQLite cannot reliably remove that complete definition with a simple `DROP COLUMN`, so the migration should rebuild the table:

1. Create `Users_New` with the final schema.
2. Verify that the old `Users` table contains zero rows.
3. Remove the old username index/table.
4. Rename `Users_New` to `Users`.
5. Create the case-insensitive email index.
6. Run `PRAGMA foreign_key_check`.

### 6.2 Guard against automatic data loss

Before applying the empty-database migration, the migrator must inspect the existing schema and row count.

If `Username` exists and `Users` contains rows, application startup must stop with an actionable error explaining that the manual conversion tool is required. It must never drop or transform populated users automatically.

Schema detection must also recognize a database already converted by the manual tool:

- `Email` exists;
- `Username` does not exist;
- the email uniqueness index exists;
- the token table and required indexes exist.

When all invariants are present, the migrator can record the migration versions as already represented by the schema.

### 6.3 Manual conversion tool

Create a small one-time .NET console tool under `scripts/UserEmailMigration`. This is a migration utility, not a revival of the archived application.

Inputs:

- explicit database path;
- local JSON mapping of old usernames to email addresses;
- dry-run mode by default;
- required `--confirm` switch for changes.

The mapping file must be ignored by Git and must never be logged.

Execution sequence:

1. Require the web application to be stopped.
2. Create a timestamped backup beside the selected database.
3. Verify migration versions 1-6 and the expected old schema.
4. Verify that the mapping covers every user exactly once.
5. Reject missing users, unknown users, duplicate emails, and invalid emails.
6. Disable foreign-key enforcement before starting the table-rebuild transaction.
7. Create the final user table.
8. For each old user:
   - preserve `Id` and `CreatedAt`;
   - assign the normalized mapped email;
   - set `EmailVerifiedAtUtc` to the shared UTC conversion time;
   - set `PreferredCulture` to null unless explicitly provided;
   - generate a new salt;
   - hash the former username as the password.
9. Create the token table and final indexes.
10. Replace the old table without modifying recipe rows.
11. Run `PRAGMA foreign_key_check` and uniqueness checks.
12. Verify user counts and recipe ownership counts before committing.
13. Commit only when every validation succeeds.
14. Re-enable foreign keys and print aggregate results only.

Rollback consists of keeping the application stopped and restoring the timestamped backup.

## 8. Registration and verification flow

1. Receive email, password, and password confirmation.
2. Validate all input server-side.
3. Normalize the email.
4. Apply endpoint and IP rate limiting.
5. In one database transaction:
   - handle an existing email safely;
   - create the unverified user;
   - create a registration-verification token expiring in 24 hours.
6. Commit before calling the external provider.
7. Render the message using the culture captured for the registration request.
8. Send through `IEmailSender`.
9. Show the check-email page without creating a cookie or JWT.

If sending fails, retain the user and token. Show a safe retry message and make the resend flow available. Do not delete the account or roll back the committed registration solely because the provider is unavailable.

### Verification link behavior

- The email link performs a GET that displays a confirmation page.
- GET must not consume the token, protecting against email-security scanners that open links automatically.
- The page submits a CSRF-protected POST.
- The POST hashes the supplied token and consumes it transactionally.
- Verification sets `EmailVerifiedAtUtc`, marks the token used, and revokes sibling registration tokens in one transaction.
- Verification does not automatically authenticate the user. The user logs in afterward.

## 9. Resend verification flow

Always return a generic response such as:

> If this address has an account awaiting verification, a new message will be sent.

For a valid unverified account, one transaction must:

1. enforce the persisted resend cooldown;
2. revoke the active registration token;
3. create a fresh 24-hour token;
4. commit before sending.

Recommended initial limits:

- registration: 5 attempts per IP per hour;
- resend: one issuance per account per minute and at most 5 per day;
- token-confirmation POST: 10 attempts per IP per 10 minutes;
- email change: 3 requests per authenticated user per hour;
- login: a moderate IP-based limiter with generic failures.

Use ASP.NET Core's built-in rate limiter for in-memory IP policies and token issuance history for persistent per-account resend limits. Do not add CAPTCHA unless real abuse makes it necessary.

## 10. Email-address management

Requesting an email change requires:

- an authenticated cookie session;
- the current password;
- a normalized, valid, currently unused target email.

The service creates an email-change token with the proposed address in `TargetEmail`. The existing verified email remains active until confirmation.

Confirmation must:

1. require the authenticated account and a CSRF-protected POST;
2. validate token hash, purpose, account, target email, expiry, and token state;
3. recheck target-email uniqueness;
4. atomically replace `Users.Email`;
5. set `EmailVerifiedAtUtc` to the new verification time;
6. mark the token used;
7. revoke competing email-change tokens;
8. sign out the current MVC session and require login with the new email;
9. notify the previous email address after commit.

The database email uniqueness index is the final defense when two users concurrently attempt to claim the same email.

A notification failure must be logged without tokens or addresses and must not roll back a completed email change.

Existing JWTs may remain valid until their current 60-minute expiry because authorization is based on user ID. Invalidating every JWT immediately would require a security-version column and database-backed validation on authenticated requests, which is disproportionate for this change.

## 11. Authentication integration and cutover

Verification must be enforced at every authentication boundary:

- login checks `EmailVerifiedAtUtc`;
- registration never signs in;
- `extension-complete` reloads the user by ID and checks verification rather than trusting cookie claims;
- `exchange-code` reloads and rechecks the user before issuing a JWT;
- extension authentication codes store only the user ID;
- current email is loaded when claims or a JWT are created;
- cookie and JWT name claims contain email;
- `/api/authentication/me` returns `email` instead of `username`.

For deployment:

- change the authentication cookie name or version so existing username cookies are rejected;
- rotate the JWT signing key, or keep the application unavailable for longer than the configured JWT lifetime;
- update Chrome extension and Web authentication tests for the email response contract.

These checks prevent a pre-deployment cookie or extension flow from becoming a verification bypass.

## 12. Email delivery and configuration

Configuration keys:

```text
Resend:ApiToken
Resend:FromAddress
Application:PublicBaseUrl
```

Local development:

- store `Resend:ApiToken` with .NET User Secrets;
- use `FakeEmailSender` by default;
- require an explicit setting to enable real delivery.

Deployment:

- supply the secret as `Resend__ApiToken` through the hosting secret store;
- never commit it to `appsettings.json`;
- never expose it to browser JavaScript or the Chrome extension;
- use a sending-only Resend key restricted to the verified sender domain;
- configure and verify the sender domain's DNS records before production sending;
- configure `Application:PublicBaseUrl` as an HTTPS origin.

The application must never construct verification links from an untrusted request `Host` header.

### Reliability decision

A transactional outbox is not justified for the application's current size.

Use this simpler sequence:

1. commit account/token state;
2. attempt delivery;
3. preserve recoverable state when delivery fails;
4. allow resend;
5. use a stable provider idempotency key based on the token row when retrying the same provider request.

Duplicate delivery is harmless because token consumption is single-use and atomic.

## 13. Email templates and localization

Culture precedence:

1. authenticated user's `PreferredCulture`;
2. validated culture cookie mirrored from that preference;
3. browser `Accept-Language`;
4. English fallback.

Configure supported cultures as `en-US` and `ro-RO`, with English as the fallback.

For registration:

- resolve culture from the request;
- persist it on the token before sending;
- reuse the stored culture if sending is later moved to background processing.

For authenticated account messages:

- use `PreferredCulture` when set;
- otherwise use the current supported request/browser culture.

Templates must be separate from controllers and business logic and provide:

- localized subject;
- safe HTML body;
- plain-text alternative;
- confirmation URL;
- 24-hour-expiry text.

Initial templates required:

- registration verification in English;
- email-change verification in English;
- previous-address change notification in English.

When a Romanian template is not yet available, render English. Adding Romanian later should require only another template/resource set.

## 14. Security requirements

- Normalize email before every lookup and write.
- Enforce uniqueness at the database level.
- Handle uniqueness races without exposing internal errors.
- Use generic registration and resend responses to reduce enumeration.
- Use a generic login error covering invalid credentials and unverified email.
- Apply antiforgery validation to every MVC POST.
- Require HTTPS in production.
- Keep cookies `Secure`, `HttpOnly`, and configured with an appropriate `SameSite` mode.
- Retain the existing local-only redirect validation.
- Do not log passwords, raw tokens, token hashes, full confirmation URLs, API keys, or email bodies.
- Set `Referrer-Policy: no-referrer` on confirmation pages.
- Avoid third-party assets on token-bearing pages.
- Redirect to a clean URL after successful token consumption.
- Keep token replacement and consumption transactional.
- Use fixed-time password-hash comparison.
- Treat the unique email index as the final concurrency defense.
- Use safe exception messages for provider and SQLite failures.

### Deferred operational cutover — not part of implementation execution

## 17. Acceptance criteria

- [ ] `Username` no longer exists in the active user schema or authentication paths.
- [ ] Archived console code is not modified or restored to the active solution.
- [ ] Obsolete JSON user authentication remnants are removed from active Core code.
- [ ] Every active user has one required, normalized, case-insensitively unique email.
- [ ] Existing user IDs and recipe ownership are preserved.
- [ ] Converted accounts are ordinary verified accounts, not legacy exceptions.
- [ ] Automatic migration refuses a populated username-based database.
- [ ] New users cannot authenticate before verification.
- [ ] Registration and verification never automatically create a cookie or JWT.
- [ ] Verification tokens are random, hashed, purpose-specific, single-use, and expire after 24 hours.
- [ ] GET requests never consume tokens.
- [ ] Resend revokes the previous token and is rate-limited.
- [ ] Email changes keep the previous address active until atomic confirmation.
- [ ] Cookie, authentication-code, and JWT flows all enforce verification.
- [ ] Resend-specific code is isolated in Infrastructure.
- [ ] API keys are loaded only from secrets.
- [ ] English HTML and plain-text templates exist with localization fallback.
- [ ] Browser language and explicit user preference follow the defined precedence.
- [ ] Provider failure leaves registration recoverable.
- [ ] Automated tests use only the fake email sender.
- [ ] The one-time conversion is backed up, dry-runnable, validated, and reversible.
