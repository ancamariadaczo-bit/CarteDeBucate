# Plan 3 - Roadmap pentru serviciul fotografiilor retetelor

## Rolul acestui document

Acest fisier este indexul principal pentru implementarea suportului foto din Core.

Implementarea nu se mai executa direct dintr-un singur plan mare. Munca este impartita in sase planuri independente, ordonate si verificabile separat:

1. `MD files/11A. RECIPE_PHOTO_FOUNDATIONS_PLAN.md`;
2. `MD files/11B. RECIPE_PHOTO_FILE_STORAGE_PLAN.md`;
3. `MD files/11C. RECIPE_PHOTO_SERVICE_OPERATIONS_PLAN.md`;
4. `MD files/11D. RECIPE_PHOTO_RECIPE_DELETION_PLAN.md`;
5. `MD files/11E. RECIPE_PHOTO_RECONCILIATION_PLAN.md`;
6. `MD files/11F. RECIPE_PHOTO_COMPOSITION_PLAN.md`.

Acest index pastreaza imaginea de ansamblu, limitele si deciziile comune. Detaliile de implementare, fisierele modificate si verificarile se afla in subplanul corespunzator.

## Scop general

Construieste in Core suport pentru fotografiile locale ale retetelor, folosind:

- fisiere locale pentru continutul binar;
- `IRecipePhotoRepository` pentru metadata;
- `IRecipeRepository` pentru verificarea retetelor;
- `ICurrentUserContext` pentru izolarea datelor utilizatorilor;
- staging si carantina pentru coordonarea sigura dintre filesystem si SQLite;
- reconciliere conservatoare pentru operatii intrerupte.

Rezultatul trebuie sa poata fi folosit ulterior de Web, App si backup ZIP, dar aceste sase planuri nu conecteaza Web sau App si nu implementeaza ZIP.

Prima versiune functioneaza numai pentru `StorageMode.Database`. Modul JSON nu afiseaza si nu gestioneaza fotografii.

## Regula obligatorie de lucru pentru toate subplanurile

Executa exact un singur pas mic si apoi opreste-te complet.

Dupa fiecare pas:

1. arata fiecare fisier modificat;
2. explica scopul fiecarei proprietati, metode si ramuri de comportament adaugate;
3. explica liniile care schimba comportamentul si grupeaza numai liniile pur mecanice;
4. spune de ce modificarea apartine acelui fisier;
5. nu rula niciun test si nu rula niciun build;
6. indica exact comanda pe care trebuie sa o ruleze utilizatorul;
7. explica ce demonstreaza verificarea ceruta;
8. raporteaza riscurile si limitarile observate;
9. asteapta rezultatul verificarii si aprobarea explicita;
10. nu continua fara comanda explicita a utilizatorului.

Nu combina pasi. Pentru orice alegere care modifica un contract aprobat, opreste-te si cere decizia utilizatorului.

Interdictia de a rula teste sau build-uri se aplica tuturor subplanurilor, inclusiv verificarilor finale.

## Dependinte deja implementate prin planul 2

- `RecipePhotoOrigin` cu `Unspecified`, `RecipeSource` si `UserUpload`;
- `RecipePhoto` cu `CreatedAtUtc`, `DisplayOrder` si `Origin`;
- `IRecipePhotoRepository`, inclusiv `AddForUser`;
- `DatabaseRecipePhotoRepository`;
- tabela si indexul `RecipePhotos`;
- foreign keys activate explicit pentru conexiunile SQLite;
- `ON DELETE CASCADE` de la `RecipePhotos` la `Recipes`;
- factory-ul database al repository-ului foto.

Daca aceste dependinte sunt schimbate pe parcurs, subplanul afectat trebuie oprit si actualizat. Nu crea o a doua varianta paralela.

## Limite comune

- Modifica numai `CarteDeBucate.Core` si testele relevante din `CarteDeBucate.Tests`.
- Nu modifica `CarteDeBucate.Web`.
- Nu modifica `CarteDeBucate.App`.
- Nu modifica `JsonRecipeRepository`.
- Nu crea storage foto pentru modul JSON.
- Nu salva bytes in SQLite.
- Nu accepta path-uri finale furnizate de utilizator.
- Nu expune `StorageFileName`, tokenuri interne sau path-uri absolute prin modelele publice.
- Nu presupune ca extensia, MIME-ul sau lungimea declarata de apelant sunt corecte.
- Resursele altui utilizator sunt raportate public ca inexistente, nu ca acces interzis.
- Nu implementa `RestorePhotoAsync`, ZIP sau `System.IO.Compression`.
- Nu porni automat reconcilierea din Web sau App.

## Ordinea obligatorie si rezultatul fiecarui subplan

### 11A - Fundatii, contracte si validare

Defineste configurarea, formatele, limitele, modelele publice, rezultatele, validarea continutului, normalizarea numelui si `IRecipePhotoService`.

Rezultat verificabil: regulile pure si API-ul public exista si au teste unitare, fara implementarea filesystem-ului sau a serviciului.

### 11B - File storage

Implementeaza radacina locala, staging, fisiere finale, citire, carantina si enumerarea interna necesara reconcilerului.

Rezultat verificabil: intregul ciclu de viata al fisierului poate fi testat intr-un director temporar, fara DB.

### 11C - Operatiile serviciului foto

Implementeaza `RecipePhotoService`, inclusiv adaugarea, listarea, citirea si stergerea individuala.

Rezultat verificabil: orchestrarea dintre storage si repository este testata cu fake-uri, inclusiv compensarea la erori.

### 11D - Stergerea unei retete

Implementeaza coordonatorul pentru lotul de fisiere al unei retete si il integreaza optional in `RecipeLibraryService`.

Rezultat verificabil: stergerea unei retete coordoneaza DB si filesystem, iar modul JSON ramane neschimbat.

### 11E - Reconciliere

Implementeaza recuperarea conservatoare pentru staging, carantina si fisiere finale orfane.

Rezultat verificabil: operatiile intrerupte mai vechi de pragul configurat sunt tratate controlat, fara stergerea automata a orfanilor finali.

### 11F - Compunere si verificare finala

Adauga factory-urile, rezolvarea path-ului foto, verificarea pregatirii pentru ZIP si checklistul final.

Rezultat verificabil: infrastructura Core poate fi construita complet prin factory-uri, fara integrare in Web sau App.

## Decizii comune aprobate

### Formate si limite

- JPEG: `image/jpeg`, extensia `.jpg`;
- PNG: `image/png`, extensia `.png`;
- WebP: `image/webp`, extensia `.webp`;
- `MaxFileSizeBytes = 10 * 1024 * 1024`;
- `MaxPhotosPerRecipe = 20`;
- `ReconciliationMinimumAge = 24 ore`.

### Directorul fotografiilor

- valoarea configurata implicit este `recipe-photos`;
- `AppServiceFactory` transforma configurarea intr-un path absolut;
- un path relativ este rezolvat fata de directorul bazei de date;
- un path absolut este normalizat si folosit direct;
- `FileSystemRecipePhotoStorage` primeste numai radacina absoluta;
- storage-ul creeaza radacina, staging-ul si carantina;
- radacina trebuie sa fie in afara `wwwroot`.

### Upload

- stream-ul este copiat asincron intr-un fisier staged;
- bytes reali sunt numarati si reprezinta autoritatea pentru dimensiune;
- formatul este detectat din continut;
- fisierul final primeste nume intern GUID plus extensia detectata;
- metadata este salvata numai dupa finalizarea fisierului;
- un esec DB declanseaza eliminarea compensatorie a fisierului final;
- stream-ul apelantului nu este inchis de serviciu.

### Concurenta

Prima versiune foloseste varianta simpla:

- serviciul verifica limita de 20 inainte de staging;
- serviciul calculeaza urmatorul `DisplayOrder` din starea observata;
- nu se adauga lock-uri, tranzactii speciale sau metode repository noi;
- doua uploaduri perfect simultane pot depasi limita sau pot primi acelasi `DisplayOrder`;
- aceasta este o limitare cunoscuta si acceptata pentru prima versiune.

### Stergere si compensare

- stergerea unei fotografii foloseste carantina inaintea stergerii metadata;
- un fisier deja lipsa nu blocheaza stergerea metadata;
- daca DB esueaza, fisierul este restaurat;
- daca stergerea definitiva esueaza dupa succesul DB, operatia ramane succes cu cleanup amanat;
- la stergerea unei retete, un esec inainte de DB restaureaza lotul si opreste stergerea;
- un esec de cleanup dupa succesul DB este logat si lasat reconcilerului.

### Reconciliere

- `IRecipePhotoStorage` include enumerarea interna necesara reconcilerului;
- enumerarea nu expune path-uri absolute;
- se proceseaza numai fisiere mai vechi decat pragul configurat;
- DB trebuie citita cu succes inaintea oricarei mutatii filesystem;
- fisierele finale orfane sunt raportate, nu sterse automat.

### API

- numai `AddPhotoAsync` este asincron;
- listarea, citirea si stergerea raman sincrone;
- stream-ul returnat de citire apartine consumatorului;
- API-ul public foloseste coduri de rezultat, nu textul mesajelor;
- nu exista `AccessDenied` pentru resursele altui utilizator.
