# Plan 3 - Serviciul pentru gestionarea fotografiilor retetelor

## Scop

Construieste in Core un serviciu care salveaza, valideaza, citeste, listeaza si sterge fotografiile retetelor, folosind:

- fisiere locale pentru continutul binar;
- `IRecipePhotoRepository` pentru metadata;
- `IRecipeRepository` pentru verificarea retetei;
- `ICurrentUserContext` pentru izolarea datelor utilizatorilor;
- staging si carantina pentru coordonarea sigura dintre filesystem si SQLite.

Serviciul trebuie sa poata fi folosit ulterior de Web, App si backup ZIP, dar acest plan nu conecteaza UI-ul Web sau App si nu implementeaza ZIP.

Acest plan se executa numai dupa finalizarea `MD files/10. RECIPE_PHOTOS_DATABASE_PLAN.md`.

Prima versiune a fotografiilor functioneaza numai pentru `StorageMode.Database`. Modul JSON nu afiseaza si nu gestioneaza fotografii.

## Decizii de design aprobate

### Separarea responsabilitatilor

- `IRecipePhotoStorage` lucreaza strict cu fisiere si tokenuri opace;
- `FileSystemRecipePhotoStorage` gestioneaza radacina locala, staging, fisiere finale si carantina;
- `RecipePhotoValidator` detecteaza si valideaza formatul continutului staged;
- `IRecipePhotoService` expune cazurile de utilizare normale;
- `RecipePhotoService` coordoneaza storage, repository, timp, logging si user context;
- `IRecipePhotoDeletionCoordinator` expune numai coordonarea necesara stergerii unei retete;
- `RecipeLibraryService` ramane punctul unic prin care consumatorii sterg o reteta;
- `RecipePhotoReconciliationService` repara conservator operatiile filesystem intrerupte.

### Formate si limite

Formatele initiale permise sunt:

- JPEG: `image/jpeg`, extensia `.jpg`;
- PNG: `image/png`, extensia `.png`;
- WebP: `image/webp`, extensia `.webp`.

Foloseste un enum `RecipePhotoFormat` cu `Unknown = 0`, `Jpeg = 1`, `Png = 2`, `WebP = 3` si un singur registru intern care asociaza formatul, MIME-ul normalizat, extensia si verificarea semnaturii.

Optiunile initiale sunt:

- `MaxFileSizeBytes = 10 * 1024 * 1024`;
- `MaxPhotosPerRecipe = 20`;
- `ReconciliationMinimumAge = 24 ore`.

Optiunile sunt configurabile pentru dezvoltator sau administrator, dar utilizatorul obisnuit nu trebuie sa configureze nimic si nu primeste setari UI in acest plan.

### Directorul fotografiilor

- valoarea implicita este `recipe-photos`;
- un path absolut configurat este folosit direct;
- un path relativ este rezolvat fata de directorul bazei de date;
- directorul este creat de storage, nu de `AppSettings`;
- staging-ul si carantina sunt sub aceeasi radacina pentru a permite mutari atomice pe acelasi filesystem;
- radacina fotografiilor trebuie sa fie in afara `wwwroot`;
- Web va servi ulterior continutul numai prin controller si serviciul autorizat, nu drept fisier static.

### Uploadul staged

Fluxul aprobat este:

1. verifica reteta, proprietarul si limita de 20 de fotografii;
2. copiaza asincron stream-ul intr-un fisier staged cu nume intern;
3. numara bytes reali si opreste copierea imediat ce depaseste limita;
4. deschide continutul staged ca stream seekable pentru validare;
5. detecteaza formatul dupa semnatura si confirma concordanta cu MIME-ul declarat;
6. normalizeaza MIME-ul si numele original;
7. finalizeaza fisierul prin rename la GUID plus extensia formatului detectat;
8. salveaza metadata in DB;
9. daca DB refuza sau esueaza, elimina compensatoriu fisierul final;
10. daca eliminarea compensatorie esueaza, scrie warning si lasa reconcilerul sa raporteze fisierul orfan.

Stream-ul primit apartine apelantului si nu este inchis de serviciu.

### Normalizarea numelui original

- elimina orice componenta de director, inclusiv separatori `/` si `\\`;
- elimina caracterele de control si spatiile exterioare;
- limiteaza rezultatul la 255 de caractere;
- inlocuieste extensia declarata cu extensia formatului detectat;
- daca numele devine gol, foloseste `photo` plus extensia detectata;
- numele original normalizat este numai metadata si nu participa la construirea path-ului fizic.

### Stergerea in doua faze

Fluxul aprobat pentru o fotografie este:

1. citeste metadata prin metoda filtrata potrivita;
2. muta atomic fisierul final in carantina si primeste un token opac;
3. sterge metadata prin metoda repository potrivita;
4. dupa succesul DB sterge definitiv fisierul din carantina;
5. daca DB esueaza sau nu sterge niciun rand, restaureaza fisierul;
6. daca fisierul lipsea deja, continua stergerea metadata, intoarce succes cu avertisment si scrie warning in log.

Uploadul staged si stergerea staged folosesc tipuri diferite, astfel incat tokenurile sa nu poata fi confundate.

### Reconcilierea dupa oprire neasteptata

- proceseaza numai fisiere mai vechi decat `ReconciliationMinimumAge`, implicit 24 de ore;
- sterge uploadurile staged abandonate;
- pentru carantina, restaureaza fisierul daca metadata exista si il sterge definitiv daca metadata nu mai exista;
- ruleaza numai dupa ce baza de date a fost deschisa si citita cu succes;
- fisierele finale care nu sunt referite de DB sunt raportate in log, dar nu sunt sterse automat in prima versiune;
- descriptorii persistenti ai carantinei nu contin path-uri absolute.

### API sincron si asincron

- `AddPhotoAsync` este asincron si primeste `CancellationToken`;
- listarea, deschiderea continutului si stergerea raman sincrone;
- curatarea compensatorie necesara dupa crearea fisierului final nu este abandonata din cauza anularii apelantului;
- stream-ul returnat de citire apartine consumatorului, care trebuie sa il inchida.

### Backup ZIP viitor

Planul curent pregateste enumerarea si citirea continutului pentru export, dar nu implementeaza `RestorePhotoAsync`.

Un backup viitor va pastra:

- `OriginalFileName` normalizat;
- `CreatedAtUtc`;
- `DisplayOrder`;
- `Origin`;
- continutul fotografiei.

La restaurare se vor regenera sau recalcula:

- `Id`;
- `RecipeId`, prin maparea la reteta nou importata;
- `StorageFileName`;
- `ContentType`, din continut;
- `FileSize`, din bytes reali.

## Contractele publice tinta

### Codurile rezultatelor

Adauga un enum `RecipePhotoResultCode` care poate exprima cel putin:

- `Success`;
- `DeletedMetadataFileWasMissing`;
- `CleanupPending`;
- `InvalidRecipeId`;
- `RecipeNotFound`;
- `PhotoNotFound`;
- `PhotoLimitReached`;
- `EmptyContent`;
- `FileTooLarge`;
- `UnsupportedFormat`;
- `InvalidContent`;
- `ContentFileMissing`;
- `StorageFailure`;
- `PersistenceFailure`.

Nu adauga `AccessDenied`; resursele altui utilizator sunt raportate ca inexistente.

### Metadata publica

`RecipePhotoInfo` contine:

- `Id`;
- `RecipeId`;
- `OriginalFileName`;
- `ContentType`;
- `FileSize`;
- `CreatedAtUtc`;
- `DisplayOrder`;
- `Origin`.

Nu contine `StorageFileName` sau path-uri.

### Rezultatele serviciului

- `RecipePhotoResult`: `IsSuccess`, `Code`, `Message`, `Photo`;
- `RecipePhotosResult`: `IsSuccess`, `Code`, `Message`, `Photos`;
- `RecipePhotoContentResult`: `IsSuccess`, `Code`, `Message`, `Content`, `ContentType`, `OriginalFileName`.

O lista goala este succes daca reteta exista. Pe esec, `Content` este `null`. Logica consumatorilor foloseste `Code`, nu textul din `Message`.

### Metodele serviciului

```csharp
Task<RecipePhotoResult> AddPhotoAsync(
    int recipeId,
    Stream content,
    string originalFileName,
    string declaredContentType,
    long? declaredLength,
    RecipePhotoOrigin origin,
    CancellationToken cancellationToken = default);

RecipePhotosResult GetPhotosForRecipe(int recipeId);
RecipePhotoContentResult GetPhotoContent(int photoId);
RecipePhotoResult DeletePhoto(int photoId);
```

Lungimea declarata este optionala si poate respinge anticipat un upload evident prea mare, dar dimensiunea reala este intotdeauna calculata in timpul copierii.
