# Plan 17 - Salvarea retetei editate din extensia Chrome

## Scop

Adauga in pagina `edit.html` a extensiei Chrome posibilitatea de a salva in Cookbook versiunea curenta a formularului, dupa editare.

Fluxul tinta este:

1. utilizatorul extrage o reteta din popup;
2. utilizatorul deschide `Edit Recipe`;
3. editorul afiseaza valorile extrase;
4. utilizatorul modifica numele, sursa, ingredientele sau instructiunile;
5. editorul valideaza valorile curente din formular;
6. `Save to Cookbook` trimite catre API valorile editate si validate, nu obiectul extras initial;
7. dupa salvare reusita, editorul ramane deschis, butonul de salvare ramane disabled, iar `Print / Save PDF` continua sa fie disponibil.

Aceasta functionalitate creeaza o reteta noua in Cookbook. Nu transforma salvarea intr-un update al unei retete deja existente.

## Regula obligatorie de lucru pentru agent

Executa exact un singur pas mic din acest document, apoi opreste-te complet.

Dupa fiecare pas:

1. arata exact fisierele modificate;
2. explica pe scurt schimbarea si motivul ei;
3. nu incepe automat pasul urmator;
4. ruleaza testele automate relevante si build-ul atunci cand sunt necesare pentru verificarea pasului curent;
5. arata comenzile rulate si rezultatul lor;
6. indica utilizatorului numai verificarile manuale care nu pot fi inlocuite de testele automate;
7. asteapta rezultatul verificarilor si aprobarea explicita a utilizatorului;
8. considera mesajul `pasul urmator` aprobare pentru exact un singur pas nou.

Agentul este autorizat sa ruleze fara aprobare suplimentara testele, build-urile si comenzile de verificare relevante pentru pasul implementat. Verificarea ramane proportionala cu schimbarea si nu trebuie sa includa proiecte neafectate.

Proiectul `CarteDeBucate.ChromeExtension` nu are in prezent un script separat de build; verificarea sa automata disponibila este `npm test`. Nu inventa un build nou numai pentru acest plan. Daca un pas ulterior introduce sau necesita o comanda reala de build, agentul o ruleaza si raporteaza rezultatul.

Nu porni automat aplicatia Web si nu incerca sa automatizezi verificarile interactive din Chrome decat daca utilizatorul cere explicit acest lucru. Aceste verificari raman checkpoint-uri manuale.

Nu face commit, push, reset, revert, schimbari generale de formatare sau modificari in afara scopului acestui plan fara o cerere explicita.

Daca implementarea necesita schimbarea unui contract stabilit in acest document, agentul se opreste si cere decizia utilizatorului inainte de schimbare.

## Starea actuala

### Editorul

- `CarteDeBucate.ChromeExtension/edit.html` contine formularul de editare si actiunile `Print / Save PDF` si `Cancel`.
- `CarteDeBucate.ChromeExtension/controllers/editController.js` citeste valorile formularului numai la submit-ul pentru printare.
- `validateAndBuildEditedRecipe()` din `editLogic.js` valideaza si construieste deja versiunea editata a retetei.
- Dupa validare, editorul scrie versiunea editata in cheia `recipeToPrint` si navigheaza aceeasi fereastra la `print.html`.
- Editorul nu verifica autentificarea si nu poate salva in Cookbook.

### Salvarea existenta din popup

- Popup-ul principal afiseaza `Save to Cookbook` dupa extragerea unei retete.
- Pentru un utilizator neautentificat, butonul este vizibil, dar disabled, iar zona de autentificare este vizibila.
- Pentru un utilizator autentificat, butonul trimite `currentRecipe` catre `saveRecipeToApi()`.
- `saveRecipeToApi()` trimite `name`, `sourceUrl`, `ingredients` si `steps` la `POST /api/recipes`.
- API-ul intoarce `recipeId` dupa o salvare reusita si respinge o reteta duplicata dupa `SourceUrl` in contextul utilizatorului curent.

### Autentificarea existenta

- JWT-ul extensiei este pastrat in `chrome.storage.local` prin `auth/authStorage.js`.
- `auth/authenticationState.js` verifica tokenul prin endpointul `/api/authentication/me`.
- Service worker-ul gestioneaza mesajul `LOGIN` si executa flow-ul `chrome.identity.launchWebAuthFlow`.
- Popup-ul foloseste un buton separat `Log in`; apasarea pe `Save to Cookbook` nu porneste autentificarea.
- Butonul `Create account` din popup nu are in prezent event listener. Acest plan nu copiaza si nu implementeaza acel buton in editor.

## Contractul functional tinta

### Formularul si valorile salvate

- `Save to Cookbook` foloseste valorile curente din formular in momentul clickului.
- Nu trimite obiectul extras initial daca formularul a fost modificat.
- Salvarea si printarea refolosesc aceeasi cale de colectare, normalizare si validare.
- Regulile existente raman neschimbate:
  - `Recipe name` este obligatoriu;
  - `Source URL` este obligatoriu si trebuie sa fie un URL absolut `http` sau `https` cu host;
  - trebuie sa ramana cel putin un ingredient;
  - trebuie sa ramana cel putin o instructiune;
  - valorile sunt normalizate conform `validateAndBuildEditedRecipe()`.
- `Print / Save PDF` din editor isi pastreaza comportamentul actual.
- Printarea directa din popup ramane neschimbata.

### Imaginea

- `Image URL` ramane editabil pentru preview si printare.
- `Image URL` nu este trimis la `POST /api/recipes`.
- Nu modifica `CreateRecipeRequest`, `Recipe`, serviciile Core, repository-urile, schema SQLite sau tabela `RecipePhotos`.
- Nu descarca, nu copiaza si nu salveaza fisiere de imagine.
- Nu modifica planurile existente pentru fotografii.

### Utilizator neautentificat

La deschiderea editorului:

- formularul poate fi editat;
- `Print / Save PDF` este activ;
- `Save to Cookbook` este vizibil, dar disabled;
- editorul afiseaza mesajul exact `Sign in to save this recipe to your cookbook.`;
- editorul afiseaza un buton separat `Log in`;
- editorul nu afiseaza si nu adauga `Create account` in acest plan.

Apasarea pe `Save to Cookbook` nu porneste autentificarea. Butonul disabled nu are efect.

### Login din editor

- `Log in` trimite mesajul existent `LOGIN` catre service worker.
- Nu duplica `chrome.identity.launchWebAuthFlow` in editor.
- Dupa login reusit:
  - valorile editate raman in formular;
  - zona de autentificare se ascunde;
  - `Save to Cookbook` devine activ.
- Dupa login anulat sau esuat:
  - valorile editate raman in formular;
  - `Save to Cookbook` ramane disabled;
  - mesajul vizibil devine `Sign in was not completed. Please try again.`;
  - eroarea tehnica este trimisa si catre `reportError`.

### Utilizator autentificat

La deschiderea editorului:

- starea autentificarii este rezolvata prin dependentele existente `getAccessToken`, `getCurrentUser`, `removeAccessToken` si `resolveAuthenticationState`;
- daca tokenul este valid, zona de autentificare este ascunsa si `Save to Cookbook` este activ;
- editorul ramane utilizabil pentru editare si printare chiar daca verificarea autentificarii sau serverul Web esueaza.

### Starile salvarii

Inaintea requestului:

- formularul este validat;
- daca validarea esueaza, API-ul nu este apelat;
- erorile sunt afisate in sumarul de validare existent.

In timpul requestului:

- `Save to Cookbook` devine disabled imediat;
- zona de stare afiseaza `Saving...`;
- clickurile multiple nu pot porni requesturi paralele.

Dupa salvare reusita:

- editorul ramane deschis;
- textul butonului ramane `Save to Cookbook`;
- butonul ramane disabled pentru restul vietii acelei instante de editor;
- zona de stare afiseaza `Recipe saved successfully.`;
- `Print / Save PDF`, `Cancel` si campurile formularului raman utilizabile;
- nu navigheaza automat la Cookbook si nu deschide o alta fereastra.

Dupa salvare esuata:

- `Save to Cookbook` este reactivat daca utilizatorul este autentificat;
- zona de stare afiseaza `The recipe could not be saved. Reason: <reason>`;
- valorile formularului raman intacte;
- `Print / Save PDF` ramane disponibil;
- eroarea tehnica este trimisa si catre `reportError`.

O instanta noua a editorului nu mosteneste starea locala `saved` a instantei inchise. Daca utilizatorul deschide din nou editorul si este autentificat, butonul de salvare este din nou activ. Backend-ul ramane responsabil sa respinga duplicatele.

## Decizii de implementare

### O singura functie pentru construirea retetei editate

Extrage din handlerul actual de submit o functie interna mica ce:

1. citeste toate valorile curente din formular;
2. apeleaza `validateAndBuildEditedRecipe(originalRecipe, formValues)`;
3. afiseaza sumarul de validare cand datele sunt invalide;
4. intoarce reteta editata cand datele sunt valide.

Atat printarea, cat si salvarea apeleaza aceasta functie. Nu duplica regulile de validare in handlerul de salvare.

### Separarea efectelor

- Calea de printare continua sa apeleze dependentele existente `saveRecipe()` si `navigateToPrint()`.
- Calea de Cookbook apeleaza o dependenta noua injectata in controller, `saveRecipeToApi(editedRecipe)`.
- Controllerul nu citeste direct tokenul si nu apeleaza direct `fetch`.
- `edit.js` compune dependenta `saveRecipeToApi` folosind clientul API si `getAccessToken()`, la fel ca popup-ul.
- `edit.js` compune dependenta `login` prin mesajul `LOGIN`, la fel ca popup-ul.

### Starea UI din controller

Controllerul pastreaza explicit:

- `isAuthenticated`;
- `isSaving`;
- `isSaved`.

Starea butonului este derivata din aceste valori:

```text
saveButton.disabled = !isAuthenticated || isSaving || isSaved
```

Nu schimba textul butonului pentru niciuna dintre stari.

### Initializarea editorului

- Citirea si afisarea payload-ului retetei nu depind de serverul Web.
- Formularul trebuie initializat chiar daca rezolvarea autentificarii esueaza.
- Verificarea autentificarii nu trebuie sa stearga sau sa reconstruiasca randurile formularului.
- Controllerul expune numai mecanismul minim necesar pentru actualizarea starii autentificarii dupa verificarea initiala.
- Nu muta logica DOM in `edit.js`.

### Mesaje separate

- `errorMessage` ramane pentru payload invalid, erori de initializare si erori de validare.
- Adauga o zona separata `saveStatus` pentru `Saving...`, succesul salvarii si eroarea requestului.
- Mesajul de autentificare ramane in zona `authSection`.
- `saveStatus` foloseste `role="status"` sau `aria-live="polite"`.
- O noua incercare valida curata mesajele de validare vechi care nu mai sunt relevante.
