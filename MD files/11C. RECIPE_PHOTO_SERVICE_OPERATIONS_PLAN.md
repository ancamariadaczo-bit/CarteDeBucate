# Plan 3C - Operatiile serviciului foto

## Scop

Implementeaza `RecipePhotoService` si cazurile normale de utilizare pentru o fotografie individuala:

- adaugare;
- listare;
- citirea continutului;
- stergere.

Serviciul coordoneaza regulile din planul 3A, filesystem-ul din planul 3B si repository-urile implementate prin planul 2.

## Dependinte

- planul 2 complet;
- planul 3A complet;
- planul 3B complet.

## In afara scopului

- stergerea unei retete intregi;
- reconcilierea dupa restart;
- factory-uri;
- Web, App si ZIP.

## Regula de lucru

Executa un singur pas, explica fiecare modificare de comportament, nu rula build sau teste, indica verificarea utilizatorului si asteapta aprobarea explicita.

## Dependentele serviciului

`RecipePhotoService` primeste:

- `IRecipePhotoStorage`;
- `IRecipePhotoRepository`;
- `IRecipeRepository`;
- `ICurrentUserContext?`;
- `RecipePhotoValidator`;
- `RecipePhotoFileNameNormalizer`;
- `RecipePhotoOptions`;
- `TimeProvider`;
- `ILogger<RecipePhotoService>`.

## Reguli comune

- intr-un context autentificat se folosesc metodele repository filtrate pe user;
- resursa altui utilizator este raportata ca inexistenta;
- `StorageFileName` nu paraseste serviciul;
- exceptiile tehnice sunt logate si transformate in coduri controlate;
- stream-ul primit la upload nu este inchis;
- stream-ul returnat la citire apartine consumatorului.

## Limitarea de concurenta acceptata

Prima versiune foloseste varianta simpla:

- limita de 20 este verificata in serviciu inainte de staging;
- urmatorul `DisplayOrder` este calculat din lista observata;
- nu se modifica repository-ul cu operatii atomice noi;
- nu se folosesc lock-uri;
- doua uploaduri simultane pot depasi limita sau primi acelasi `DisplayOrder`.

Aceasta limitare trebuie documentata in codul sau testele contractului, dar nu trebuie rezolvata in acest plan.

Fisier nou:

Pentru un user autentificat, reteta sau fotografia altui utilizator este raportata ca not-found.

Adauga teste pentru:

- context global;
- user corect;
- alt user;
- maparea care nu expune `StorageFileName`.

Verificare pentru utilizator: ruleaza numai testele scheletului serviciului.

Opreste-te si asteapta aprobarea.

## Pasul 2 - Implementeaza AddPhotoAsync

Fluxul aprobat:

1. valideaza `recipeId`, stream-ul, origin si metadata declarata;
2. verifica reteta in contextul curent;
3. citeste fotografiile existente;
4. verifica limita de 20;
5. calculeaza urmatorul `DisplayOrder`;
6. respinge anticipat o lungime declarata evident prea mare;
7. copiaza asincron stream-ul in staging si foloseste bytes reali;
8. deschide continutul staged ca stream seekable;
9. valideaza semnatura si MIME-ul declarat;
10. normalizeaza MIME-ul si numele original;
11. finalizeaza fisierul la GUID plus extensie detectata;
12. construieste metadata folosind `TimeProvider`;
13. foloseste `AddForUser` in context autentificat si `Add` in context global;
14. daca insertul esueaza sau este refuzat, elimina compensatoriu fisierul final;
15. daca cleanup-ul esueaza, logheaza warning si intoarce rezultatul potrivit.

Reguli suplimentare:

- operatiile noi accepta numai `RecipeSource` si `UserUpload`;
- `FileSize` foloseste numai lungimea reala;
- anularea apelantului nu abandoneaza cleanup-ul necesar dupa crearea fisierului final;
- limitarile de concurenta aprobate raman documentate.

Adauga teste cu fake-uri pentru:

- succes;
- stream non-seekable;
- limita foto;
- alt utilizator ca not-found;
- continut gol sau invalid;
- fisier prea mare;
- anulare;
- esec storage;
- esec DB;
- refuz `AddForUser`;
- esec al curatarii compensatorii.

Verificare pentru utilizator: ruleaza numai testele `AddPhotoAsync`. Ele demonstreaza orchestrarea, nu implementarea reala a filesystem-ului.

Opreste-te si asteapta aprobarea.

## Pasul 3 - Implementeaza GetPhotosForRecipe

Flux:

1. valideaza ID-ul;
2. verifica existenta retetei in contextul curent;
3. foloseste listarea normala sau filtrata pe user;
4. mapeaza fiecare element la `RecipePhotoInfo`;
5. pastreaza ordinea repository-ului.

O lista goala este succes daca reteta exista.

Adauga teste pentru lista ordonata, lista goala, reteta inexistenta, ID invalid si alt utilizator.

Verificare pentru utilizator: ruleaza numai testele `GetPhotosForRecipe`.

Opreste-te si asteapta aprobarea.

## Pasul 4 - Implementeaza GetPhotoContent

Flux:

1. valideaza ID-ul;
2. incarca metadata prin metoda filtrata potrivita;
3. daca metadata nu exista, intoarce `PhotoNotFound`;
4. deschide storage-ul numai cu numele intern din metadata;
5. returneaza stream-ul, MIME-ul normalizat si numele original normalizat.

Daca metadata exista, dar fisierul lipseste:

- intoarce `ContentFileMissing`;
- scrie warning;
- nu sterge automat metadata.

Adauga teste pentru succes, alt utilizator, metadata lipsa, fisier lipsa si eroare storage.

Verificare pentru utilizator: ruleaza numai testele `GetPhotoContent`.

Opreste-te si asteapta aprobarea.

## Pasul 5 - Implementeaza DeletePhoto

Flux:

1. valideaza ID-ul;
2. incarca metadata in contextul potrivit;
3. muta fisierul final in carantina;
4. sterge metadata prin metoda repository potrivita;
5. dupa succesul DB sterge definitiv fisierul din carantina;
6. daca DB esueaza sau nu sterge randul, restaureaza fisierul.

Reguli:

- alt utilizator primeste `PhotoNotFound`;
- fisierul lipsa nu blocheaza stergerea metadata si produce `DeletedMetadataFileWasMissing`;
- cleanup-ul esuat dupa succesul DB produce succes cu `CleanupPending`;
- tokenul de carantina nu este expus;
- esecurile tehnice sunt logate.

Adauga teste pentru succes, ID invalid, alt utilizator, fisier lipsa, esec DB, refuzul stergerii, restaurare si cleanup amanat.

Verificare pentru utilizator: ruleaza numai testele `DeletePhoto`.

Opreste-te si asteapta aprobarea.

## Pasul 6 - Verificarea finala a planului 3C

Opreste-te si asteapta aprobarea finala.
