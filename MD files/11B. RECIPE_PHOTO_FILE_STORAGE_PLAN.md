# Plan 3B - File storage pentru fotografiile retetelor

## Scop

Implementeaza ciclul de viata al fisierelor foto, independent de SQLite, retete si utilizatori.

La finalul planului, storage-ul poate:

- crea si valida structura de directoare;
- copia asincron un stream intr-un upload staged;
- deschide si abandona uploadul staged;
- finaliza uploadul printr-un fisier cu nume intern;
- deschide fisiere finale read-only;
- muta fisiere in carantina;
- restaura sau sterge definitiv continutul din carantina;
- enumera elementele interne necesare reconcilerului.

Toate testele acestui plan folosesc directoare temporare si nu necesita DB.

## Dependinte

- planul 3A pentru `RecipePhotoFormat` si optiunile aprobate;
- regulile comune din `MD files/11. RECIPE_PHOTO_SERVICE_PLAN.md`.

## In afara scopului

- `Recipe`, `RecipePhoto` si repository-urile;
- `ICurrentUserContext`;
- `RecipePhotoService`;
- codurile publice de rezultat;
- rezolvarea configurarii relative fata de DB;
- reconcilierea propriu-zisa;
- Web, App si ZIP.

## Regula de lucru

Executa un singur pas, explica fiecare modificare de comportament, nu rula build sau teste, indica verificarea utilizatorului si asteapta aprobarea explicita.

## Responsabilitatile aprobate

### Radacina

- constructorul storage-ului primeste un path absolut;
- storage-ul valideaza path-ul primit;
- storage-ul creeaza controlat radacina si subdirectoarele;
- staging-ul si carantina sunt sub aceeasi radacina ca fisierele finale;
- mutarile dintre zone raman pe acelasi filesystem;
- storage-ul nu cunoaste `AppSettings` sau `DatabasePath`.

### Nume interne

- numele finale sunt generate intern sub forma GUID plus extensie canonica;
- storage-ul nu accepta path-uri finale de la consumator;
- sunt respinse numele goale, absolute, cu `..`, separatori sau caractere de control;
- verificarea formei canonice se face inaintea oricarui acces.

### Tipuri opace

Uploadul staged si stergerea staged folosesc tipuri diferite, astfel incat tokenurile sa nu poata fi confundate.

Tokenurile:

- nu contin path-uri absolute in contract;
- nu sunt modele publice pentru Web sau App;
- pot fi create numai de storage;
- sunt validate din nou cand sunt folosite.

### Enumerarea pentru reconciler

`IRecipePhotoStorage` include operatii interne pentru enumerarea:

- uploadurilor staged;
- descriptorilor persistenti din carantina;
- fisierelor finale.

Elementele enumerate contin numai tokenuri opace, `StorageFileName` atunci cand este necesar si timpul relevant. Nu expun path-uri absolute.

## Pasul 1 - Creeaza tipurile opace si contractul storage-ului

Fisiere noi:

- `CarteDeBucate.Core/Services/Photos/StagedRecipePhotoUpload.cs`;
- `CarteDeBucate.Core/Services/Photos/StagedRecipePhotoDeletion.cs`;
- modelele interne necesare inventarului storage;
- `CarteDeBucate.Core/Services/Photos/IRecipePhotoStorage.cs`.

Contractul trebuie sa permita:

- staging asincron, cu limita de bytes si lungime reala returnata;
- deschiderea read-only a uploadului staged;
- finalizarea folosind `RecipePhotoFormat`;
- abandonarea uploadului;
- deschiderea read-only a fisierului final;
- verificarea existentei;
- mutarea in carantina;
- restaurarea din carantina;
- stergerea definitiva din carantina;
- enumerarea opaca pentru reconciliere.

Nu implementa inca filesystem-ul.

Verificare pentru utilizator: ruleaza build-ul Core. Build-ul demonstreaza separarea contractelor, nu comportamentul fisierelor.

Verificare pentru utilizator: ruleaza numai testele de radacina si path validation.

Opreste-te si asteapta aprobarea.

## Pasul 3 - Implementeaza staging-ul asincron

Implementeaza copierea intr-un fisier temporar aflat sub staging.

Reguli:

- numele temporar este generat intern;
- lungimea declarata nu reprezinta autoritatea;
- bytes reali sunt numarati;
- copierea se opreste imediat dupa depasirea limitei;
- fisierul partial este curatat la limita depasita, anulare sau eroare;
- stream-ul apelantului nu este inchis;
- nu se creeaza fisierul final.

Adauga teste pentru:

- stream seekable;
- stream non-seekable;
- continut gol;
- limita exacta;
- limita plus un byte;
- anulare;
- eroare de citire;
- absenta fisierului partial dupa esec.

Verificare pentru utilizator: ruleaza numai testele de staging. Ele demonstreaza copierea si cleanup-ul, nu validarea formatului.

Opreste-te si asteapta aprobarea.

## Pasul 4 - Implementeaza deschiderea, finalizarea si abandonarea uploadului

Implementeaza:

- deschiderea read-only a continutului staged;
- generarea GUID plus extensia canonica a formatului;
- finalizarea prin rename fara suprascriere;
- tratarea coliziunilor;
- abandonarea idempotenta.

Finalizarea primeste formatul deja detectat. Storage-ul nu detecteaza formatul si nu normalizeaza numele original.

Adauga teste pentru:

- continutul complet;
- extensia formatului;
- unicitatea numelui;
- lipsa suprascrierii;
- disparitia fisierului staged dupa succes;
- abandon repetat;
- token staged invalid.

Verificare pentru utilizator: ruleaza testele de staging si finalizare.

Opreste-te si asteapta aprobarea.

## Pasul 5 - Implementeaza citirea fisierului final

Adauga:

- verificarea existentei dupa `StorageFileName`;
- deschiderea unui stream read-only;
- rezultat intern controlat pentru fisier inexistent;
- validarea numelui inaintea accesului.

Stream-ul returnat apartine consumatorului si trebuie inchis de acesta.

Adauga teste pentru fisier existent, fisier inexistent, nume invalid si caracteristicile stream-ului read-only.

Verificare pentru utilizator: ruleaza numai testele de citire ale storage-ului.

Opreste-te si asteapta aprobarea.

## Pasul 6 - Implementeaza carantina

Implementeaza:

- mutarea prin rename a fisierului final in carantina;
- descriptorul persistent necesar recuperarii dupa restart;
- restaurarea idempotenta;
- stergerea definitiva idempotenta;
- raportarea distincta a fisierului deja inexistent.

Descriptorul persistent pastreaza numai identificatori interni, `StorageFileName` original si timpul necesar reconcilerului. Nu pastreaza path-uri absolute.

Daca forma exacta a descriptorului necesita o alegere cu impact asupra contractului, opreste pasul si prezinta optiunile inainte de implementare.

Adauga teste pentru:

- mutare;
- restaurare;
- stergere definitiva;
- fisier lipsa;
- token invalid;
- coliziune la restaurare;
- repetarea restaurarii sau stergerii.

Verificare pentru utilizator: ruleaza numai testele carantinei.

Opreste-te si asteapta aprobarea.

## Pasul 7 - Implementeaza enumerarea interna

Implementeaza operatiile din `IRecipePhotoStorage` care enumera:

- uploadurile staged si timpul lor;
- descriptorii valizi din carantina;
- fisierele finale si timpul lor.

Reguli:

- nu returna path-uri absolute;
- nu modifica fisiere in timpul enumerarii;
- raporteaza controlat intrarile invalide;
- nu decide ce trebuie sters sau restaurat;
- reconcilerul din planul 3E va lua deciziile.

Adauga teste pentru inventar gol, mai multe elemente, descriptor invalid si absenta expunerii path-ului.

Verificare pentru utilizator: ruleaza numai testele de inventar ale storage-ului.

Opreste-te si asteapta aprobarea.
