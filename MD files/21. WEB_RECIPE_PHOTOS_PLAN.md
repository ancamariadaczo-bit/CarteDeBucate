# Plan 21 - Fotografii pentru retete in Web si Chrome Extension

## Scop

Integreaza infrastructura foto existenta in aplicatia Web MVC si in fluxul de salvare al extensiei Chrome.

La finalul planului:

- utilizatorul poate selecta o fotografie cand adauga manual o reteta;
- utilizatorul poate vedea fotografiile unei retete in pagina de detalii;
- utilizatorul poate adauga si sterge fotografii din pagina de editare;
- prima fotografie poate fi afisata in lista de retete si in pagina de printare;
- importul unei retete din URL incearca sa copieze local prima imagine valida gasita pe pagina;
- extensia Chrome trimite URL-ul imaginii extrase impreuna cu reteta;
- serverul Web descarca imaginea extensiei si o salveaza local;
- metadata fotografiei este salvata in SQLite prin `IRecipePhotoService`;
- continutul fotografiei este salvat in filesystem sub `RecipePhotosPath`;
- fotografiile sunt livrate UI-ului printr-un endpoint autentificat, nu ca fisiere statice din `wwwroot`;
- stergerea unei retete din Web foloseste coordinatorul foto deja implementat.

Acest plan foloseste contractele existente din planurile 10 si 11A-11F. Nu reproiecteaza storage-ul foto.

## Decizii stabilite

### Implementarea existenta ramane neschimbata pana incepe executarea planului

- nu modifica `MD files/11F. RECIPE_PHOTO_COMPOSITION_PLAN.md`;
- nu muta rezolvarea path-ului foto din `CarteDeBucate.Web/Program.cs`;
- pastreaza implementarea curenta din `AppServiceFactory`;
- nu modifica acum codul Core deja implementat doar pentru a-l face identic cu formularea din 11F.

### RecipePhotosApiController ramane controller temporar de test

`CarteDeBucate.Web/Controllers/Api/RecipePhotosApiController.cs` exista pentru verificarea manuala a backend-ului foto.

Reguli:

- pastreaza controllerul si endpoint-urile existente;
- nu il sterge si nu il redenumi;
- nu construi UI-ul MVC prin apeluri HTTP catre acest controller;
- UI-ul MVC injecteaza si foloseste direct `IRecipePhotoService`;
- integrarea extensiei se face prin `RecipesApiController`, nu prin transformarea controllerului temporar intr-un workflow cu doua request-uri;
- securizarea sau eliminarea controllerului temporar se discuta separat, dupa finalizarea UI-ului.

### „Cel putin o fotografie” inseamna suport, nu obligativitate

Prima versiune permite salvarea uneia sau mai multor fotografii pentru o reteta, pana la limita existenta de 20.

- formularul Create permite selectarea unei fotografii initiale;
- formularul Edit permite adaugarea ulterioara a fotografiilor, cate una per request;
- fotografia nu devine camp obligatoriu al modelului `Recipe`;
- retetele vechi si importurile fara imagine valida raman utilizabile;
- stergerea ultimei fotografii este permisa;
- nu se adauga o coloana foto in tabela `Recipes`;
- `RecipePhotos` ramane singura sursa de metadata foto.

### Separarea responsabilitatilor

- `Recipe` nu primeste `ImageUrl`, `PhotoId`, bytes sau path-uri;
- URL-ul extern al imaginii exista numai ca informatie tranzitorie in fluxul de import;
- `StorageFileName` nu este trimis catre browser;
- uploadul manual foloseste `RecipePhotoOrigin.UserUpload`;
- imaginile copiate din pagina sursa sau din extensie folosesc `RecipePhotoOrigin.RecipeSource`;
- serverul valideaza din nou continutul prin `IRecipePhotoService`, chiar daca extensia a afisat deja imaginea.

### Extensia trimite URL-ul, serverul copiaza imaginea

Extensia are deja `recipe.imageUrl`. Ea trimite acest URL in JSON-ul request-ului de creare a retetei.

Serverul:

1. salveaza reteta;
2. descarca imaginea printr-un client HTTP protejat impotriva SSRF;
3. transmite stream-ul catre `IRecipePhotoService.AddPhotoAsync`;
4. salveaza metadata in SQLite si bytes in filesystem.

Nu se adauga `<all_urls>` in `manifest.json` si extensia nu descarca direct bytes de la orice CDN.

### Politica pentru succes partial

Reteta si fotografia nu pot fi salvate intr-o singura tranzactie intre SQLite si filesystem.

Politica aprobata pentru Create, Import si extensie:

- daca salvarea retetei esueaza, fotografia nu este procesata;
- daca reteta este salvata si fotografia esueaza, reteta ramane salvata;
- raspunsul sau UI-ul arata clar avertismentul despre fotografie;
- nu se sterge automat o reteta valida doar pentru ca imaginea externa a disparut sau a fost invalida;
- extensia nu retrimite automat intreaga reteta dupa un esec foto, pentru a nu crea un duplicat.

## Starea curenta relevanta

- `IRecipePhotoService` poate adauga, lista, citi si sterge fotografii;
- fisierele foto sunt in afara `wwwroot`;
- `RecipePhotosApiController` poate testa uploadul si stergerea backend-ului;
- `RecipesController` returneaza in prezent modele `Recipe` direct catre Details si Print;
- `RecipeFormViewModel` nu contine un `IFormFile`;
- Create si Edit nu au `multipart/form-data`;
- importul C# nu extrage un URL de imagine;
- extractoarele JavaScript din extensie produc deja `imageUrl`;
- `recipeApiClient.js` elimina in prezent `imageUrl` din payload-ul trimis serverului;
- `RecipesApiController` returneaza deja `recipeId`, necesar pentru asocierea fotografiei;
- serviciul Web pentru retete este construit fara coordinatorul foto, desi Core il suporta.

## In afara scopului

- mutarea `RecipePhotosPath` sau servirea directa din `wwwroot`;
- stocare foto pentru modul JSON;

## Contractele tinta

### Modele Web

Adauga modele Web dedicate in loc sa extinzi modelul persistent `Recipe` cu date de prezentare:

- `RecipeDetailsViewModel`: `Recipe` si lista ordonata `Photos`;
- `RecipePrintViewModel`: `Recipe` si `PrimaryPhotoId` nullable;
- `RecipeIndexItemViewModel`: `RecipeSummary` si `PrimaryPhotoId` nullable;
- `RecipePhotoUploadViewModel`: `RecipeId` si `IFormFile? Photo` pentru actiunea separata de upload din Edit.

`RecipeFormViewModel` primeste numai fotografia initiala necesara Create:

```csharp
public IFormFile? Photo { get; set; }
```

Nu adauga `[Required]` pe fotografie.

### Endpoint MVC pentru continut

Adauga un controller MVC dedicat, autentificat cu schema Cookie:

```text
GET /RecipePhotos/Content/{photoId}
```

Endpoint-ul:

- apeleaza `IRecipePhotoService.GetPhotoContent(photoId)`;
- se bazeaza pe filtrarea userului din serviciul Core;
- returneaza `FileStreamResult` numai pe succes;
- seteaza MIME-ul rezultatului, dar nu seteaza `FileDownloadName`, astfel incat imaginea sa poata fi randata inline;
- returneaza 404 pentru fotografie inexistenta, ID invalid sau fotografie a altui user;
- nu dezvaluie `StorageFileName` sau path-ul fizic;
- lasa MVC sa inchida stream-ul dupa trimiterea raspunsului;
- foloseste headere private/no-store pentru continutul utilizatorului.

### Rezultatul importului din URL

`RecipeImportResult` primeste un camp tranzitoriu:

```csharp
public string? ImageUrl { get; set; }
```

`ImageUrl` nu este copiat in `Recipe` si nu este persistent in tabela `Recipes`.

### Request-ul extensiei

`CreateRecipeRequest` primeste:

```csharp
public string? ImageUrl { get; set; }
```

Valoarea este optionala, dar daca exista trebuie sa fie un URL HTTP sau HTTPS valid.

Raspunsul 201 al API-ului pastreaza `recipeId` si adauga un rezultat foto controlat, de exemplu:

```json
{
  "message": "Recipe saved successfully.",
  "recipeId": 42,
  "photo": {
    "status": "Saved",
    "message": "The recipe photo was saved."
  }
}
```

Statusurile minime sunt `NotProvided`, `Saved` si `Failed`. Un status foto `Failed` nu schimba raspunsul de creare a retetei din 201 in eroare.
