# Global Session Invalidation Implementation Plan

- [ ] Phase 1 - Add the user security version and database migration.
- [ ] Phase 2 - Add atomic persistence and the invalidation service.

## 1. Goal and scope

Add a small, reusable mechanism that invalidates every existing authentication credential belonging to one user. It must work for:

- MVC authentication cookies used by the web application;
- JWT bearer tokens used by the Chrome extension;
- future features such as Sign Out from All Devices, password changes, password resets, and other account-security operations.

The mechanism will use a persisted `SecurityVersion` on the user. Each cookie and JWT contains the version that existed when it was issued. Advancing the stored version makes all older credentials invalid.

This task provides infrastructure only. It does **not** implement:

- a Sign Out from All Devices endpoint, button, or view;
- change-password or reset-password functionality;
- integration with existing email-management operations;
- session lists, per-device sessions, refresh tokens, or individual-session revocation.

## 2. Development-environment assumptions

There is currently no production deployment. Users and the development database can be managed manually. Therefore:

- no rolling-deployment or mixed-version compatibility mechanism is needed;
- it is acceptable for all existing development cookies and JWTs to become invalid once validation is enabled;
- credentials without a security-version claim will be rejected;
- the database migration and application changes can be applied together;
- no Redis cache, distributed coordination, or multi-instance infrastructure will be introduced.

These assumptions simplify the implementation without weakening the core security behavior.

## 3. Existing architecture

### Authentication

- Authentication is custom and does not use ASP.NET Core Identity.
- `CarteDeBucate.Core/Services/Authentication/AuthenticatinService.cs` verifies the email and password and returns a `User`.
- `CarteDeBucate.Web/Controllers/AccountController.cs` creates the MVC cookie in `SignInUser`.
- `CarteDeBucate.Web/Services/Authorization/JwtTokenService.cs` creates extension JWTs.
- `CarteDeBucate.Web/Program.cs` configures the default cookie scheme and the explicit JWT bearer scheme.
- Cookies and JWTs currently contain user ID and email claims but no session/security version.
- Neither authentication scheme currently checks the database after the credential's normal cryptographic validation succeeds.

### Extension authentication flow

The Chrome extension authentication flow is:

```text
MVC cookie
  -> /api/authentication/extension-complete
  -> short-lived, single-use authentication code
  -> /api/authentication/exchange-code
  -> JWT
```

`AuthenticationApiController.ExchangeCode` reloads the user before issuing the JWT. The temporary code currently stores only the user ID and expiration.

### Persistence and migrations

- Users are stored in SQLite.
- `User`, `IUserRepository`, and `DatabaseUserRepository` are the existing user model and persistence components.
- `DatabaseInitializer` creates the current schema for fresh databases.
- `DatabaseMigrator` applies hand-written transactional migrations.
- Migration 7 is currently the latest migration, so this feature should use migration 8.
- Repository and migration tests use temporary SQLite database files.

### Chrome extension behavior

The extension already has the required client behavior:

- `/api/authentication/me` returning `401` causes the stored JWT to be removed;
- the editor and side panel switch to an unauthenticated state and ask the user to sign in again;
- network failures and non-`401` server errors do not remove the stored token.

No production extension changes are expected. Existing tests should be reused to verify this behavior.

## 4. Design decisions

### 4.1 Persisted security version

Add this property to `User`:

```csharp
public long SecurityVersion { get; set; } = 1;
```

Add this column to `Users`:

```sql
SecurityVersion INTEGER NOT NULL DEFAULT 1
```

Version `1` is sufficient for all existing and new development users. A signed 64-bit value avoids any realistic exhaustion concern.

### 4.2 Atomic invalidation

Invalidate all sessions with one database-side update:

```sql
UPDATE Users
SET SecurityVersion = SecurityVersion + 1
WHERE Id = @UserId;
```

Do not read the version into application code and then write `version + 1`. The arithmetic must happen in SQLite so simultaneous invalidation calls cannot overwrite each other.

Expose the operation through a small service:

```csharp
public interface IGlobalSessionInvalidationService
{
    bool InvalidateAllSessions(int userId);
}
```

`true` means exactly one user was updated; `false` means the user was not found. The service is independent of controllers and authentication schemes.

### 4.3 Credential claim

Define one shared claim-name constant, recommended as:

```text
security_version
```

Store the version as an invariant-culture decimal string in both cookies and JWTs.

A credential is invalid when:

- the user ID claim is missing or invalid;
- the security-version claim is missing, duplicated, malformed, or non-positive;
- the user no longer exists;
- the claimed version differs from the persisted version.

Credentials issued before this feature have no version claim and will be rejected. In the current development-only environment, this one-time sign-in reset is acceptable and requires no compatibility branch.

### 4.4 Temporary extension authentication codes

The temporary extension authentication code must also contain the security version of the cookie session that created it.

At code exchange:

1. consume the single-use code;
2. reload the user;
3. compare the code version with the user's persisted version;
4. reject the code if the versions differ;
5. otherwise issue a JWT containing that version.

This small addition prevents a code created immediately before invalidation from creating a fresh JWT afterward.

### 4.5 Request validation

Use one shared scoped validator for both authentication schemes. It should:

1. parse the user ID and security-version claims;
2. load only the user's persisted security version;
3. return valid only when the values match exactly.

Use small authentication event classes to connect the validator to ASP.NET Core:

- cookie validation rejects the principal and removes the invalid cookie;
- JWT validation fails authentication, causing protected API endpoints to return `401 Unauthorized`.

Existing issuer, audience, signature, lifetime, login redirect, and authorization behavior must remain unchanged.

### 4.6 Database failures

If SQLite cannot be queried, authentication must not silently succeed. Let the exception produce a server failure rather than converting it into an invalid-session `401`.

This distinction matters to the extension:

- `401` means the credential is definitively invalid and may be removed;
- `5xx` or a network failure is temporary, so the stored token must be preserved.

### 4.7 Performance and caching

Perform one primary-key database lookup for each structurally valid authenticated credential. Do not add caching now.

The application has no production traffic to justify cache complexity, and a cache could delay revocation. If request volume later makes the lookup significant, measure it first and design caching as a separate feature.

### 4.8 Future password operations

No password feature is implemented here. When password change or reset is added, the password update and `SecurityVersion` increment must occur in the same database transaction.

Do not build a transaction abstraction now. Add the composite repository operation when the password feature exists and its exact persistence requirements are known.

### 4.9 Multiple application instances

The current development application does not need distributed invalidation. The persisted version already survives application restarts.

If multiple application instances are introduced later, they must use the same authoritative user database. The existing process-local extension authentication-code store is also a separate limitation that must be addressed before horizontal scaling.

## 7. Simple development rollout

No staged deployment is necessary.

1. Back up the development database if its contents matter.
2. Stop the application.
3. Apply the completed code changes.
4. Start the application and allow migration 8 to run.
5. Sign in again in the web application and Chrome extension.
6. Run the full test suites.

All existing cookies and JWTs without the new claim will be invalid. This is expected.

## 8. Future safeguards without current overengineering

The following are deliberately deferred, but the design leaves clear paths for them:

- **Password change/reset:** update the password and increment `SecurityVersion` in one repository transaction.
- **Production deployment:** define a rollout strategy when a real production topology exists.
- **Multiple instances:** use shared authoritative persistence and replace the process-local authentication-code store.
- **Caching:** add only after measurements show the per-request primary-key lookup is a real problem.
- **Security auditing:** expand structured audit logging when account-security endpoints are introduced.

Deferring these items does not weaken the current invalidation mechanism. It avoids building abstractions for requirements that do not yet exist.

## 9. Explicit non-goals

Do not add any of the following during this implementation:

- Sign Out from All Devices UI or endpoint;
- change-password or reset-password behavior;
- active-session tables or session management screens;
- per-token deny lists or refresh tokens;
- Redis or in-memory security-version caches;
- distributed locking or messaging;
- a general unit-of-work framework;
- unrelated authentication or repository refactoring.
