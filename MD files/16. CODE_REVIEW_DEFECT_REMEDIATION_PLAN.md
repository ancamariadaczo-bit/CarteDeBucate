# Plan 16 - Remedierea defectelor identificate la review-ul complet

## Scop

Acest document acopera, intr-un singur plan, cele cinci defecte confirmate prin review-ul snapshot-ului complet din branch-ul `main`:

1. `HttpClient` este creat si abandonat pentru fiecare scope Web;
2. importul unei retete din URL permite requesturi SSRF si raspunsuri nelimitate;
3. validarea centrala permite salvarea unui `SourceUrl` care nu este HTTP sau HTTPS;
4. repository-ul SQLite trateaza username-urile diferit fata de repository-ul JSON si fata de testele serviciului;
5. importul de backup poate salva retete invalide si poate ramane aplicat partial dupa un esec.

Planul remediaza cate un singur defect o data. Dupa implementarea si verificarea unui defect, agentul se opreste complet si asteapta aprobarea explicita a utilizatorului inainte de a incepe defectul urmator.

## Regula obligatorie de lucru pentru agent

Executa exact un singur pas mic din acest document, apoi opreste-te complet.

Dupa fiecare pas:

1. arata exact fisierele modificate;
2. explica pe scurt schimbarea si motivul ei;
3. mentioneaza ce ramane de facut in defectul curent;
4. nu incepe automat pasul urmator;
5. nu rula build, teste, restore, aplicatia Web sau aplicatia console;
6. indica utilizatorului comanda de verificare relevanta, daca pasul poate fi verificat;
7. asteapta rezultatul si aprobarea explicita a utilizatorului;
8. considera mesajul `pasul urmator` aprobare pentru exact un singur pas nou.

La finalul fiecarui defect exista un checkpoint suplimentar obligatoriu. Chiar daca utilizatorul a aprobat pasii mici din acel defect, agentul nu incepe defectul urmator pana cand utilizatorul nu confirma explicit rezultatul complet al defectului curent.

Agentul poate rula teste sau build numai daca utilizatorul ii cere explicit acest lucru intr-un mesaj ulterior. Comenzile de verificare din acest document sunt, implicit, pentru utilizator.

Nu face commit, push, reset, revert, schimbari de formatare generala sau modificari in afara defectului curent fara o cerere explicita.

## Principii comune

- Pastreaza comportamentul existent care nu este legat de defectul remediat.
- Scrie mai intai testul care reproduce defectul atunci cand acest lucru este practic.
- Actualizeaza testele existente numai atunci cand contractul corect s-a schimbat intentionat.
- Nu slabi o asertiune doar ca testul sa treaca.
- Daca un test existent contrazice contractul din acest plan, explica diferenta si opreste-te pentru decizie.
- Nu combina doua defecte intr-un singur increment, chiar daca ating acelasi fisier.
- Mesajele trimise clientului nu trebuie sa expuna IP-uri interne, stack trace-uri, cai locale sau exceptii brute.
- Toate modificarile de schema SQLite trebuie sa fie compatibile cu bazele de date existente si sa aiba teste de migrare.

## Ordinea obligatorie

Ordinea este aleasa dupa dependente:

1. corecteaza ciclul de viata al `HttpClient`;
2. foloseste noua compunere pentru protectia SSRF;
3. corecteaza validarea URL-ului salvat;
4. unifica identitatea case-insensitive a username-ului;
5. adauga importul de backup validat si atomic.

Protectia SSRF nu trebuie combinata cu mutarea la `IHttpClientFactory`. Primul defect schimba numai ownership-ul clientului; al doilea schimba politica requesturilor de retea.

Validarea sintactica a unui `SourceUrl` salvat este diferita de validarea destinatiei accesate de server:

- o reteta poate stoca numai un URL absolut `http` sau `https`;
- importul server-side aplica in plus restrictii de retea si accepta numai destinatii publice.

## In afara scopului

- Nu modifica flow-ul codului temporar sau emiterea JWT-ului.
- Nu adauga refresh tokens, revocare JWT sau logout nou pentru extensie.
- Nu modifica extractoarele, editorul sau printarea extensiei Chrome.
- Nu modifica planurile pentru fotografii.
- Nu introduce Entity Framework Core; repository-urile raman SQLite ADO.NET si JSON.
- Nu face refactorizari cosmetice si nu redenumi fisiere fara o nevoie directa.
- Nu adauga rate limiting sau o politica noua de parole in acest plan.
- Nu remedia alte observatii descoperite incidental. Documenteaza-le separat si cere aprobarea utilizatorului.

## Defectul 1 - Ciclul de viata incorect al `HttpClient`

### Scenariul actual

`RecipesController` cere importerul in constructor pentru toate actiunile sale. Din acest motiv, un client nou poate fi creat inclusiv pentru requesturi de lista, detalii, editare sau stergere, nu doar pentru importul din URL. Clientul si handler-ul lui nu au un owner care sa le elibereze determinist.

### Riscul

- se creeaza inutil pool-uri noi de conexiuni;
- sub trafic poate aparea presiune pe socketuri si resurse;
- configurarea de timeout, user-agent si handler este ascunsa intr-un constructor si nu poate fi administrata coerent prin DI;
- Web si consola pot ajunge sa configureze diferit acelasi client.

### Contractul tinta

- `RecipeImporter` primeste obligatoriu un `HttpClient`; nu mai are constructor care il creeaza intern;
- Web foloseste un typed client sau `IHttpClientFactory`;
- aplicatia console detine un singur client pe durata procesului si il elibereaza la inchidere;
- user-agent-ul si timeout-ul sunt configurate intr-un singur loc reutilizabil;
- acest defect nu schimba inca regulile URL, redirecturile sau limita raspunsului.

## Defectul 2 - SSRF si raspuns nelimitat la importul din URL

### Scenariul actual

`RecipeImporter.ImportFromUrlAsync` verifica doar ca valoarea este un URL absolut HTTP/HTTPS, apoi executa requestul server-side. Sunt acceptate destinatii precum:

- `http://127.0.0.1` si `http://[::1]`;
- adrese RFC1918, de exemplu `10.0.0.0/8` sau `192.168.0.0/16`;
- adrese link-local, inclusiv `169.254.169.254`;
- hostname-uri care rezolva catre retele private;
- redirecturi de la un URL public catre o destinatie interna.

`GetStringAsync` incarca intregul raspuns in memorie, fara o limita aplicativa.

### Riscul

Un utilizator autentificat poate folosi serverul pentru requesturi catre servicii interne, pentru probing sau pentru endpointuri care au efecte la `GET`. Un raspuns foarte mare poate consuma memoria procesului.

### Contractul tinta

- sunt acceptate numai schemele `http` si `https`;
- sunt acceptate numai porturile 80 si 443;
- toate adresele rezolvate pentru host trebuie sa fie public-routable;
- sunt respinse loopback, private, link-local, multicast, unspecified, reserved/documentation si variantele IPv4-mapped IPv6;
- adresa aprobata trebuie sa fie si adresa folosita la conexiune, evitand o simpla verificare DNS urmata de o a doua rezolvare necontrolata;
- redirecturile sunt urmarite manual, cu maximum 5 redirecturi, iar fiecare destinatie este reverificata;
- redirectul de la HTTPS la HTTP este respins;
- raspunsul este citit streaming si are o limita implicita de 5 MiB;
- erorile de politica folosesc mesajul public generic de import esuat si nu expun detalii de retea.

### Pasul 6 - Scrie testele politicii de destinatie

Adauga teste parametrizate pentru clasificarea adreselor:

- IPv4 si IPv6 publice acceptate;
- `127.0.0.1`, `::1` si unspecified respinse;
- retele private IPv4 si unique-local IPv6 respinse;
- link-local si metadata IP respinse;
- multicast, reserved si IPv4-mapped private respinse;
- un hostname cu cel putin o rezolvare nepublica este respins integral.

Rezolutia DNS trebuie sa fie injectabila sau izolata printr-o interfata mica, pentru ca testele sa fie deterministe si sa nu foloseasca internetul real.

Nu modifica inca requesturile. Opreste-te si asteapta aprobarea utilizatorului.

### Pasul 7 - Implementeaza politica de retea la momentul conexiunii

Introdu o componenta Core dedicata politicii outbound pentru import, separata de `UrlValidator`.

Handler-ul folosit pentru import trebuie:

- sa aiba `AllowAutoRedirect = false`;
- sa rezolve hostul in mod controlat;
- sa verifice toate adresele rezultate;
- sa conecteze socketul numai la o adresa deja aprobata;
- sa respecte anularea requestului.

Nu aplica aceasta politica altor clienti HTTP ai aplicatiei.

Opreste-te si asteapta aprobarea utilizatorului.

### Pasul 8 - Implementeaza redirecturile sigure

In componenta care descarca pagina:

- trateaza explicit statusurile de redirect;
- rezolva URL-urile relative fata de URL-ul curent;
- valideaza din nou schema, portul, hostul si adresele destinatiei;
- opreste flow-ul dupa maximum 5 redirecturi;
- respinge downgrade-ul HTTPS -> HTTP;
- inchide fiecare raspuns intermediar.

Adauga teste pentru:

- redirect public -> public permis;
- redirect public -> loopback respins;
- lant prea lung respins;
- redirect fara `Location` tratat controlat;
- downgrade HTTPS -> HTTP respins.

Opreste-te si asteapta aprobarea utilizatorului.

### Pasul 9 - Limiteaza raspunsul si citeste-l streaming

Inlocuieste `GetStringAsync` cu un request care foloseste `ResponseHeadersRead`.

Comportamentul trebuie sa fie:

- respinge imediat un `Content-Length` mai mare de 5 MiB;
- opreste citirea daca stream-ul depaseste 5 MiB chiar cand headerul lipseste sau este fals;
- pastreaza decodarea corecta a textului paginii;
- inchide response-ul si stream-ul in toate ramurile;
- continua sa intoarca mesajul public existent pentru download esuat.

Adauga teste pentru limita declarata si pentru depasirea limitei in timpul citirii.

Opreste-te si asteapta aprobarea utilizatorului.

### Pasul 10 - Leaga handler-ul sigur in Web si consola

Actualizeaza configurarea introdusa la defectul 1 astfel incat atat Web, cat si consola sa foloseasca acelasi handler sigur pentru import.

Nu modifica alte servicii HTTP si nu introduce exceptii pentru localhost in mediul Development. Daca este nevoie de import local in viitor, acesta trebuie discutat separat si activat explicit, nu permis implicit.

Opreste-te si asteapta aprobarea utilizatorului.

## Defectul 4 - Username case-insensitive inconsistent

### Scenariul actual

`JsonUserRepository` si fake-ul de test folosesc comparatie case-insensitive. Testul serviciului confirma ca `Anca` trebuie considerat duplicat daca exista `anca`.

`DatabaseUserRepository` foloseste insa `WHERE Username = $username`, iar coloana SQLite este `TEXT UNIQUE` cu collation implicita case-sensitive. In productia Web, `anca` si `Anca` pot deveni doua conturi diferite, iar loginul depinde de casing.

### Riscul

- acelasi contract se comporta diferit intre JSON, fake si SQLite;
- pot aparea identitati vizual echivalente;
- utilizatorul se poate loga cu alt casing si poate crede ca retetele lui au disparut;
- verificarea `GetByUsername` urmata de `INSERT` nu protejeaza singura impotriva inregistrarilor concurente.

### Decizia finala aprobata

Varianta initiala cu `NormalizedUsername` si `UsernameNormalizer` a fost eliminata la cererea utilizatorului. Pentru acest proiect este suficienta garantarea unicitatii case-insensitive direct pe coloana existenta `Username`.

Se presupune explicit ca datele existente sunt consistente si nu contin deja `anca` si `Anca` ca utilizatori diferiti. Daca presupunerea este falsa, SQLite refuza natural crearea indexului unic; migrarea nu incearca sa stearga, sa redenumeasca sau sa uneasca utilizatori.

### Contractul final

- schema pastreaza o singura coloana `Username`;
- forma originala, trimuita de `AuthenticationService`, ramane valoarea salvata si afisata;
- SQLite impune unicitatea prin indexul `IX_Users_Username_NoCase` pe `Username COLLATE NOCASE`;
- `DatabaseUserRepository.GetByUsername` foloseste aceeasi collation `NOCASE` pentru lookup;
- `JsonUserRepository` si fake-ul continua sa foloseasca `StringComparison.OrdinalIgnoreCase`;
- `anca` si `Anca` nu pot deveni doua conturi SQLite diferite;
- loginul cu alt casing gaseste acelasi cont;
- nu se introduce normalizare Unicode completa si nu se adauga o a doua coloana;
- un insert concurent duplicat este oprit de indexul bazei de date, fara o noua abstractie pentru traducerea exceptiei SQLite.

`COLLATE NOCASE` este contractul simplificat ales aici. Nu promite echivalenta completa pentru toate diferentele Unicode de casing sau compozitie.

### Pasul 16 - Experimentul de normalizare, eliminat

`UsernameNormalizer` si testele sale au fost create initial, apoi eliminate dupa simplificarea aprobata. Nicio componenta de normalizare si nicio coloana `NormalizedUsername` nu raman in implementare.

- migratorul recunoaste indexul deja existent si inregistreaza migrarea fara sa o reaplice.

### Pasul 18 - Testele de schema si migrare, finalizat

## Defectul 5 - Importul backup este nevalidat si neatomic

### Scenariul actual

`RecipeBackupService.ImportFromJsonContent` parseaza documentul si apoi apeleaza `AddRecipe` pentru fiecare reteta.

Problemele sunt doua parti ale aceleiasi operatii de import:

1. retetele nu trec prin `RecipeValidator`, deci un backup poate introduce nume/URL/data/lista de ingrediente sau pasi invalide;
2. fiecare reteta este persistata imediat. Daca o inserare ulterioara esueaza, metoda intoarce esec, dar retetele anterioare raman salvate.

La retry, retetele deja salvate pot fi raportate ca duplicate, desi primul import a fost raportat ca esuat.

### Contractul tinta

- intregul document este citit, mapat si validat inainte de prima scriere;
- o singura reteta invalida invalideaza tot importul si nu modifica persistenta;
- duplicatele fata de repository si duplicatele din acelasi backup sunt calculate inainte de batch;
- `ImportedCount` si `SkippedCount` raman corecte;
- toate retetele acceptate sunt trimise repository-ului printr-un singur contract batch;
- SQLite foloseste o singura tranzactie pentru retete, ingrediente si pasi;
- JSON construieste rezultatul complet in memorie, il scrie intr-un fisier temporar din acelasi director si inlocuieste atomic fisierul tinta;
- un esec lasa starea initiala neschimbata;
- V1 si V2 raman compatibile, iar `Id`/`UserId` din backup nu sunt restaurate;
- userul curent continua sa fie aplicat tuturor retetelor importate.

### Pasul 22 - Testele serviciului pentru validare inainte de scriere, finalizat

`RecipeBackupServiceTests` verifica acum:

- esec cu zero persistari cand o reteta ulterioara este invalida;
- URL invalid pentru V1 si V2;
- ingrediente sau pasi lipsa;
- `SavedAt` implicit;
- import valid printr-un singur batch;
- duplicate interne numarate si trimise o singura data.

`FakeRecipeRepository` inregistreaza batch-ul si numarul apelurilor.

### Pasul 23 - Contractul batch in repository, finalizat

`IRecipeRepository` expune `AddRecipes(IReadOnlyCollection<Recipe> recipes)`. SQLite, JSON si fake-ul implementeaza contractul, iar semantica metodei existente `AddRecipe` a ramas neschimbata.

### Pasul 24 - Batch-ul tranzactional SQLite, finalizat

`DatabaseRecipeRepository.AddRecipes` foloseste o singura conexiune si o singura tranzactie pentru retete, ingrediente si pasi. Commit-ul se face dupa ultima reteta, rollback-ul acopera intregul batch, iar ID-urile obiectelor sunt setate numai dupa commit.

Testul de integrare provoaca o incalcare de foreign key la a doua reteta si confirma ca prima reteta nu ramane in baza de date si niciun obiect nu primeste ID.

### Pasul 25 - Batch-ul atomic JSON, finalizat

`JsonRecipeRepository.AddRecipes`:

- incarca lista o singura data;
- genereaza ID-uri consecutive fara coliziuni;
- construieste si serializeaza rezultatul complet in memorie;
- scrie intr-un fisier temporar din acelasi director;
- muta fisierul temporar atomic peste tinta;
- seteaza ID-urile obiectelor numai dupa succes;
- curata fisierul temporar dupa succes si dupa esec.

Testele confirma ID-urile, pastrarea fisierului existent la un esec de pregatire si absenta fisierelor temporare reziduale.
