# Implementare autentificare optionala in Web

## Scop

Adaugam in `CarteDeBucate.Web` autentificare optionala, controlata din fisierul de setari, similar cu aplicatia console.

Cand autentificarea este dezactivata:

- Web-ul ramane utilizabil fara login;
- listele, cautarea, detaliile, editarea, stergerea, importul din URL si backup-ul folosesc contextul fara user curent;
- comportamentul ramane apropiat de Web-ul actual.

Cand autentificarea este activata:

- userul trebuie sa se autentifice pentru a folosi zona de retete;
- retetele noi primesc `UserId` al userului logat;
- lista, cautarea, detaliile, editarea, stergerea, importul din URL si backup-ul folosesc doar retetele userului logat.

## Decizii confirmate pentru prima iteratie

1. Cand `AuthenticationEnabled = true`, Web-ul va avea atat `Register`, cat si `Login`, similar cu aplicatia console.
2. Cand un user este logat, nu vede retetele vechi cu `UserId = null`.
   - Comportamentul actual din console este acelasi: userul logat vede doar retetele cu `UserId` egal cu userul curent.
3. Cand `AuthenticationEnabled = true`, ruta default `/` duce direct la login daca userul nu este autentificat.
4. Navbar-ul va afisa logout cand userul este logat.
5. Pentru prima iteratie folosim cookie authentication standard ASP.NET Core, fara ASP.NET Identity complet.

## Decizii amanate

- Nu introducem admin/roluri in prima iteratie.
- Nu introducem pagina de administrare useri in prima iteratie.
- Nu introducem flow de invite sau resetare parola in prima iteratie.
- Ideea cu admin care administreaza userii ramane o imbunatatire ulterioara.

## Context observat in cod

### Configurare existenta

- `CarteDeBucate.Web/appsettings.json` are deja:

```json
{
  "DatabasePath": "recipes.db",
  "AuthenticationEnabled": false
}
```

- `CarteDeBucate.Web/Program.cs` citeste `DatabasePath`, dar nu citeste inca explicit `AuthenticationEnabled` pentru a decide flow-ul Web.
- `CarteDeBucate.Core/Configuration/AppSettings.cs` citeste deja `AuthenticationEnabled` pentru aplicatia console.

### Servicii Core deja reutilizabile

- `AuthenticationService` exista deja in Core si ofera:
  - `Register(username, password)`;
  - `Login(username, password)`;
  - `Logout()`;
  - `IsLoggedIn`.
- `AuthenticationService` seteaza `ICurrentUserContext` cand login/register reuseste.
- `Program.cs` din Web inregistreaza deja:
  - `ICurrentUserContext`;
  - `IUserRepository`;
  - `IAuthenticationService`;
  - `IRecipeImporterService`;
  - `IRecipeBackupService`.

### Comportamentul actual din Core pentru retete pe user

`RecipeImporterService` este deja context-aware:

- daca `CurrentUserId` exista:
  - `GetRecipeSummaries()` foloseste `GetRecipeSummariesByUserId(CurrentUserId.Value)`;
  - `SearchRecipes(searchText)` trimite `CurrentUserId` catre repository;
  - `GetRecipeById(recipeId)` foloseste `GetRecipeByIdAndUserId(recipeId, CurrentUserId.Value)`;
  - `SaveRecipe(recipe)` seteaza `recipe.UserId = CurrentUserId.Value`;
  - `UpdateRecipe(recipe)` foloseste `UpdateRecipeForUser(recipe, CurrentUserId.Value)`;
  - `DeleteRecipe(recipeId)` foloseste `DeleteRecipeForUser(recipeId, CurrentUserId.Value)`;
  - `HasRecipesInCurrentContext()` foloseste `HasRecipesForUser(CurrentUserId.Value)`.
- daca `CurrentUserId` nu exista:
  - serviciul foloseste variantele globale, fara filtrare dupa user.

### Raspuns explicit: ce se intampla in console cu `UserId = null`

In aplicatia console, cand autentificarea este activata si userul este logat, retetele cu `UserId = null` nu sunt afisate userului logat.

Motiv:

- `CurrentUserContext` este setat dupa login;
- `RecipeImporterService.GetRecipeSummaries()` vede `CurrentUserId.HasValue`;
- se apeleaza `GetRecipeSummariesByUserId(userId)`;
- repository-ul filtreaza cu `recipe.UserId == userId`.

Retetele cu `UserId = null` apar doar in context fara user curent, adica atunci cand autentificarea este dezactivata sau nu exista login.

## Decizie recomandata pentru Web

Pastram aceeasi regula ca in console:

- fara autentificare: Web-ul vede retetele globale, inclusiv cele cu `UserId = null`;
- cu autentificare si user logat: Web-ul vede doar retetele userului logat;
- retetele `UserId = null` nu sunt amestecate in lista userului logat.

Aceasta decizie evita confuzia de ownership si foloseste deja contractele existente din Core.

## Directie tehnica propusa

Nu introducem ASP.NET Identity complet in prima iteratie. Folosim infrastructura minima:

- cookie authentication din ASP.NET Core;
- controller MVC separat, de exemplu `AccountController`;
- view models simple pentru login/register;
- un `WebCurrentUserContext` care citeste userul curent din `HttpContext.User`;
- `AuthenticationService` ramane sursa pentru verificarea parolei si crearea userilor;
- `AuthenticationEnabled` ramane setarea care decide daca rutele de retete cer login.

Motiv:

- Core are deja user repository si hashing;
- ASP.NET Identity ar introduce tabele, modele si conventii suplimentare;
- pentru proiectul actual, cookie auth + serviciul existent este mai mic si mai usor de urmarit.
- register public pastreaza prima iteratie aproape de comportamentul consolei si lasa admin/roluri pentru o etapa separata.

## Pasi mici de implementare

### Pasul 1 - Clarificarea setarii Web si testele de citire config

Scop: facem explicit faptul ca Web-ul foloseste `AuthenticationEnabled`.

Modificari:

- Adauga un model mic de configurare Web daca este nevoie, de exemplu `WebAppSettings`.
- Citeste `AuthenticationEnabled` din `builder.Configuration`.
- Pastreaza default `false`.
- Adauga teste unitare pentru parsing doar daca extragem parsing-ul intr-un helper testabil.

Validare manuala:

```bash
dotnet build --no-restore -m:1 -nr:false
```

### Pasul 2 - Context curent Web bazat pe cookie claims

Scop: serviciile Core sa primeasca `CurrentUserId` in requesturile Web autentificate.

Modificari:

- Creeaza in Web o implementare `HttpCurrentUserContext : ICurrentUserContext`.
- Citeste `UserId` si `Username` din claims.
- `IsAuthenticated` vine din `HttpContext.User.Identity`.
- Inlocuieste in DI pentru Web `CurrentUserContext` cu implementarea HTTP.

Note:

- `CurrentUserContext` simplu ramane util pentru console si teste Core.
- Pentru Web, un scoped object cu state mutabil nu este suficient intre requesturi; cookie-ul trebuie sa fie sursa adevarului.

Validare manuala:

```bash
dotnet test CarteDeBucate.Tests/CarteDeBucate.Tests.csproj --filter CurrentUserContext
```

### Pasul 3 - Cookie authentication in `Program.cs`

Scop: Web-ul poate pastra loginul intre requesturi.

Modificari:

- Adauga `AddAuthentication(...)` cu cookie scheme.
- Configureaza:
  - `LoginPath = "/Account/Login"`;
  - `LogoutPath = "/Account/Logout"`;
  - `AccessDeniedPath`, daca este nevoie.
- Adauga `app.UseAuthentication()` inainte de `app.UseAuthorization()`.
- Pastreaza `UseAuthorization()`.

Validare manuala:

```bash
dotnet build --no-restore -m:1 -nr:false
```

  - optional `ReturnUrl`.
- Creeaza `RegisterViewModel` cu:

### Pasul 5 - `AccountController` fara view-uri

Scop: stabilim contractul Web prin teste inainte de UI.

Modificari:

- Creeaza `AccountController`.
- Injecteaza:
  - `IAuthenticationService`;
  - eventual setarea `AuthenticationEnabled`.
- Actiuni propuse:
  - `Login(string? returnUrl)` GET;
  - `Login(LoginViewModel model)` POST;
  - `Register(...)` GET/POST;
  - `Logout()` POST.
- La login reusit:
  - creeaza claims pentru user id si username;
  - apeleaza `HttpContext.SignInAsync(...)`;
  - redirectioneaza la `returnUrl` local sau la `Recipes/Index`.
- La logout:
  - `SignOutAsync`;
  - redirect la login sau la recipes, in functie de `AuthenticationEnabled`.

Teste:

- Login GET returneaza view.
- Login POST cu model invalid nu cheama serviciul.
- Login POST esuat ramane in view cu eroare.
- Login POST reusit face redirect.
- Logout face redirect.

Validare manuala:

```bash

```

### Pasul 6 - Guard optional pentru rutele de retete

Scop: cand auth este activ, rutele de retete cer login; cand este dezactivat, raman publice.

Modificari:

- Adauga un filtru MVC, de exemplu `OptionalAuthenticationFilter`.
- Daca `AuthenticationEnabled = false`, filtrul nu face nimic.
- Daca `AuthenticationEnabled = true` si userul nu este autentificat:
  - redirect la `Account/Login`;
  - include `returnUrl`.
- Aplica filtrul pe controllerele care lucreaza cu retete:
  - `RecipesController`;
  - `RecipeBackupsController`.

Alternative:

- Se poate folosi `[Authorize]` conditionat prin policy, dar un filtru explicit este mai usor de urmarit in proiectul actual.

Teste:

- auth off: `RecipesController.Index` ramane accesibil;
- auth on + anonim: redirect la login;
- auth on + user: acces permis.

Validare manuala:

```bash
dotnet test CarteDeBucate.Tests/CarteDeBucate.Tests.csproj --filter OptionalAuthentication
```

### Pasul 10 - Decizie pentru retetele existente `UserId = null`

Scop: tratam explicit datele vechi.

Optiunea recomandata:

- Nu migram automat retetele `UserId = null`.
- Cand auth este off, ele raman vizibile global.
- Cand auth este on, ele nu sunt vizibile userilor logati.

Optiune alternativa:

- Adaugam un flow separat de "claim existing recipes", dar acesta trebuie planificat separat pentru ca schimba ownership-ul datelor.

## Riscuri si atentie

- `CurrentUserContext` actual este potrivit pentru console, dar Web are nevoie de context derivat din cookie/claims la fiecare request.
- Nu trebuie ca Web-ul sa ascunda retete doar in UI; filtrarea trebuie sa ramana in Core/service/repository.
- `RecipeFormViewModel` include `UserId` hidden acum. Cand auth este activ, trebuie sa ne asiguram ca userul nu poate posta un `UserId` strain si sa castige ownership. Recomandare: cand auth este activ, ignoram `UserId` din form si lasam service-ul sa seteze `CurrentUserId`.
- Backup import/export trebuie sa ramana context-aware:
  - auth off: global;
  - auth on: userul curent.
- Register public este potrivit doar pentru prima iteratie simpla. Daca Web-ul devine expus public sau multi-user serios, admin/roluri/invitatii ar trebui planificate separat.

## Ordine recomandata

1. Pastreaza deciziile confirmate pentru prima iteratie.
2. Implementeaza citirea explicita a `AuthenticationEnabled` in Web.
3. Adauga `HttpCurrentUserContext`.
4. Adauga cookie authentication.
5. Adauga `AccountController` si teste.
6. Adauga guard optional pe controllerele de retete.
7. Adauga view-urile de login/register.
8. Adauga navbar auth-aware.
9. Adauga testele pentru filtrare si ownership.
10. Decide separat daca vrei flow de claim pentru retetele `UserId = null`.
