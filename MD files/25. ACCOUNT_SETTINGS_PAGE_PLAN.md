# Plan 25 - Account Menu and Settings Page

## Objective

Add an account menu to every authenticated application page and introduce a dedicated Settings page.

The account menu will replace the currently separate username badge and Logout control. It will contain:

- the current signed-in user's identity;
- a **Settings** link;
- a **Log out** action.

The Settings page will contain exactly three sections:

1. **Preferences** - an intentionally empty placeholder for future language, measurement-unit, appearance, and similar settings;
2. **Data & Backup** - the existing JSON export and import user interface, moved from the standalone Backup page;
3. **Account** - non-functional placeholders for **Change password** and **Delete account**.

Only Data & Backup is functional in this version. JSON export, JSON import, and logout must retain their current behavior.

This feature must be implemented only in `CarteDeBucate.Web` and its directly related Web tests in `CarteDeBucate.Tests/Web`. Do not implement, mirror, or expose any part of the account menu or Settings page in Console Classic, Console Rich, or the Chrome Extension.

## Working Rules

- Implement one small step at a time and stop for user approval before starting the next step.
- Keep the implementation coordinated with the application's current UI. The supplied mockups communicate structure and interaction only; they are not pixel-perfect specifications.
- Keep visible application text in Romanian, consistent with the current authenticated Web UI. The English labels in this plan describe concepts, not required literal UI copy.
- Reuse the current Bootstrap dependency and the colors, borders, spacing, radii, shadows, typography, focus treatment, and responsive conventions already defined by the application.
- Do not add a new icon library solely for this feature. Prefer accessible inline SVG icons, CSS, or another existing project capability.
- Preserve anti-forgery protection and the existing POST-based logout, export, and import operations.
- Do not modify backup serialization, validation, ownership filtering, filenames, service calls, success/error messages, or file-upload rules.
- Do not implement password changes, account deletion, preferences, language selection, measurement units, or appearance selection in this work.
- Do not run `dotnet build`, `dotnet test`, JavaScript tests, or any other build or test command during implementation. The user will build the application and run all tests manually.
- After each implementation step, report the changed files and give the user the relevant manual checks, then stop for approval.
- Do not combine unrelated Web, API, Chrome Extension, Console, database, or backup-domain changes into this work.
- Do not modify Console Classic, Console Rich, or Chrome Extension source code, tests, manifests, assets, menus, authentication flows, import/export interfaces, or user interfaces. They are completely outside this plan.

## Current Behavior and Relevant Files

### Authenticated navigation

`CarteDeBucate.Web/Views/Shared/_Layout.cshtml` renders the shared header for authenticated application pages. It currently contains:

- the main application navigation;
- a top-level **Backup JSON** link to `RecipeBackupsController.Index`;
- a badge showing `User.Identity.Name`;
- a separate POST form that calls `AccountController.Logout`.

Because authenticated pages share this layout, the account trigger belongs in this file rather than being repeated in individual views.

### Logout

`CarteDeBucate.Web/Controllers/AccountController.cs` already provides a POST-only `Logout` action protected by anti-forgery validation. It clears the application authentication state, signs out the cookie authentication scheme, logs the event, and redirects to Login.

The account-menu Logout item must submit to this same action. Do not replace it with a GET link and do not change its controller behavior.

### JSON data and backup

`CarteDeBucate.Web/Controllers/RecipeBackupsController.cs` already owns:

- the JSON file export action;
- the uploaded JSON file import action;
- empty-file handling;
- service calls and logging;
- download-file construction;
- success and error messages.

`CarteDeBucate.Web/Views/RecipeBackups/Index.cshtml` currently renders the export and import forms. The Settings page must reuse the existing controller actions and form field contract, including the `backupFile` field name and accepted JSON file types.

`CarteDeBucate.Tests/Web/RecipeBackupsControllerTests.cs` describes the current backup action behavior. That behavior is a regression boundary for this work.

## Target Navigation and Account Menu

### Availability

Render the account trigger on every page that uses the authenticated application layout when `User.Identity.IsAuthenticated` is true. Public presentation and authentication pages that use `_PublicLayout.cshtml` remain unchanged.

Remove the top-level **Backup JSON** navigation item. Import and export must be discoverable only through **Account menu -> Settings -> Data & Backup**.

The existing recipe navigation remains unchanged:

- Recipes;
- Add recipe;
- Import from URL.

The URL-import feature is unrelated to JSON backup import and must remain in the main menu.

### Trigger content

The account trigger should sit at the right side of the authenticated navigation and include:

- a recognizable user/account icon;
- the current username from `User.Identity.Name` when space permits;
- a visual indication that it opens a menu, such as a chevron;
- an accessible name that identifies it as the current-user menu;
- correct `aria-expanded` state through the Bootstrap dropdown behavior.

The trigger and menu must work with mouse, touch, and keyboard. Focus must remain clearly visible using the application's existing focus treatment.

### Dropdown content

The dropdown contains:

1. a compact, non-interactive identity header showing the account icon, the current username, and optional supporting text equivalent to “User menu”;
2. a divider;
3. a Settings link that navigates to the Settings page;
4. a Log out button inside a POST form that targets the existing `AccountController.Logout` action.

Settings is a normal navigation link. Log out must remain a form submission so anti-forgery protection and the current logout implementation are preserved.

Do not make the identity header itself a second Settings link. Avoid duplicate or ambiguous interactive targets.

### Responsive behavior

- On desktop, align the dropdown to the right edge of its trigger so it remains inside the viewport.
- On narrow screens, keep the trigger and both actions usable within the collapsed navigation.
- Do not allow a long username to push the navigation outside the viewport; truncate or wrap it in a controlled way while preserving the full value for assistive technology or a tooltip where appropriate.
- The menu must not cover or permanently displace the page content after it closes.

## Target Settings Page

### Route and authorization

Add a dedicated authorized MVC endpoint, conceptually `SettingsController.Index`, rendered at the conventional `/Settings` route.

The Settings controller must require authentication at controller level, matching the protection used by `RecipesController` and `RecipeBackupsController`. A signed-out request must continue through the application's normal cookie-authentication challenge to Login.

The page should not require a persistent settings view model yet because all non-backup content is static and the backup forms already post directly to their existing actions. Do not add domain models or database state for placeholders.

### Page heading

Give the page a clear Settings title and a short description. Match the existing authenticated page-heading hierarchy and spacing rather than copying the mockup dimensions literally.

### Section 1 - Preferences

Render a clearly identified Preferences section in its intended first position.

This section is intentionally empty in the current version. Present a concise “coming later” or equivalent empty-state message so the section does not appear broken. It may mention the future categories:

- language;
- measurement units;
- appearance.

Do not render controls, disabled controls, forms, links, or fake values for these future settings.

### Section 2 - Data & Backup

Move the existing JSON export and import interface into this section. It contains two distinct actions.

**Export recipes**

- Explain that the user's recipes are downloaded as a JSON file.
- Submit a POST form to the existing `RecipeBackupsController.Export` action.
- Preserve the current download response, content type, generated filename, service behavior, and error handling.

**Import recipes**

- Explain that recipes can be restored or added from a JSON file.
- Keep a multipart POST form targeting the existing `RecipeBackupsController.Import` action.
- Keep the existing `backupFile` input name, JSON accept filter, required state, button behavior, server validation, and result messages.

The visual grouping may follow the supplied mockup's row-based concept, but it must match the application's current warm palette and established form/button styling. The file input must remain visible and understandable; do not reduce import to a button that hides which file was selected.

Export and Import remain independent operations. Do not combine them into one form.

### Section 3 - Account

Render two clearly labeled placeholder rows:

- **Change password**;
- **Delete account**.

These rows describe future capabilities only. They must not submit forms, open dialogs, navigate to invented routes, or call services.

Use a visibly non-functional treatment such as a “Coming soon” badge or explanatory text. Do not show active-looking Change or Delete buttons. In particular, do not use an enabled destructive red Delete button because account deletion is not implemented.

The Delete account description may explain that deletion will eventually be permanent, but it must also make the unavailable status unambiguous.

## Backup Route and Redirect Strategy

The Settings page becomes the only user-facing location for JSON import and export.

To keep existing bookmarks from ending at an obsolete page while avoiding two backup interfaces:

- keep `RecipeBackupsController` and its POST actions;
- change its `Index` endpoint into a compatibility redirect to `SettingsController.Index` rather than rendering a second backup page;
- update only the post-action destinations that currently return to `RecipeBackupsController.Index` so import results and export errors return to Settings, where the forms and shared TempData alerts are visible;
- preserve the current success/error message keys and shared-layout alert rendering;
- do not duplicate backup logic inside `SettingsController`.

This is a navigation/presentation adjustment. The bodies of the export/import operations, the `IRecipeBackupService` calls, JSON processing, and result handling remain unchanged.

After the compatibility redirect is in place, remove the obsolete standalone backup view rather than maintaining two versions of the same UI.

## Visual and Accessibility Requirements

- Treat both supplied screenshots as interaction and information-hierarchy references only.
- Coordinate the result with `CarteDeBucate.Web/wwwroot/css/site.css` and the current Bootstrap-based application UI.
- Reuse the application's CSS custom properties such as `--cb-surface`, `--cb-text`, `--cb-muted`, `--cb-primary`, and `--cb-border` instead of introducing an unrelated grayscale design.
- Keep the Settings content inside the existing authenticated page container and surface treatment.
- Use semantic headings and sections in a logical order: one page `h1`, followed by section `h2` headings.
- Decorative icons must be hidden from assistive technology. Meaningful icon-only controls must have accessible text.
- Do not rely on icons or color alone to distinguish actions or placeholder states.
- Maintain sufficient touch-target sizes and color contrast.
- Preserve visible keyboard focus for the account trigger, Settings link, Logout button, file input, and backup buttons.
- Ensure dropdown markup does not create invalid nested interactive controls.
- Keep the page usable at mobile widths without horizontal scrolling.
- Keep the account menu usable when JavaScript-enhanced Bootstrap behavior is loaded through the existing layout. Do not introduce custom JavaScript unless an identified requirement cannot be met by the bundled Bootstrap dropdown behavior.

## Acceptance Criteria

1. Every authenticated page using `_Layout.cshtml` shows one current-user account trigger in the shared header.
2. The trigger communicates the signed-in user and exposes a dropdown with Settings and Log out.
3. The dropdown is keyboard accessible, has visible focus, reports its expanded state, and remains usable on desktop and mobile.
4. Settings opens the authorized `/Settings` page.
5. Log out submits to the existing POST `AccountController.Logout` action with anti-forgery validation.
6. Logging out still clears the authentication context and cookie and redirects to Login exactly as it does now.
7. The separate username badge and standalone Logout navigation item are removed.
8. The **Backup JSON** item is removed from the top navigation.
9. URL-based recipe import remains in the top navigation and is unchanged.
10. The Settings page contains exactly three top-level sections in this order: Preferences, Data & Backup, Account.
11. Preferences contains only a clear empty/future-state message and no functional controls.
12. Data & Backup contains the existing JSON export and JSON import capabilities.
13. Export still uses the existing backup service and returns the same JSON download contract and filename pattern.
14. Import still accepts the same JSON file field and uses the same validation, service call, messages, and ownership behavior.
15. Import success, import failure, missing-file failure, and export failure return the user to Settings and show the existing shared-layout message.
16. Change password and Delete account are unmistakably non-functional placeholders.
17. No password-change or account-deletion endpoint, service, storage, modal, or confirmation flow is introduced.
18. The old `/RecipeBackups` page redirects to Settings and does not expose a second copy of the backup UI.
19. Signed-out users cannot open Settings or use the backup operations.
20. The finished UI follows the current application's Romanian content, warm palette, Bootstrap conventions, and responsive layout rather than copying the mockups literally.
21. No database schema or backup-domain changes are made.
22. The agent does not run a build or tests; the user performs all automated and manual verification.

## Implementation Steps

### Step 1 - Lock the Settings authorization and navigation contract in tests

Add focused tests before production changes:

- `SettingsController` requires `[Authorize]` at controller level;
- `SettingsController.Index` returns its default view;
- the legacy `RecipeBackupsController.Index` destination is expected to redirect to Settings;
- existing backup POST tests continue to require the same service calls and file results;
- import success, import failure, missing-file failure, and export failure expect their non-file redirects to return to Settings.

Do not weaken or replace the existing assertions that verify the export content type, JSON payload, filename extension, input content, TempData keys, or service invocation.

Do not run the tests. Report the changed test files and stop for approval.

### Step 2 - Add the authorized Settings endpoint and page shell

Add `CarteDeBucate.Web/Controllers/SettingsController.cs` with:

- controller-level authorization;
- a GET `Index` action;
- no backup service dependency;
- no account-management dependency;
- no write action.

Add `CarteDeBucate.Web/Views/Settings/Index.cshtml` with the page heading and the three semantic sections in the required order. At this step, include only the empty Preferences state and the non-functional Account placeholders; reserve the existing forms for Step 4.

Do not add a view model or database state without a demonstrated need.

Do not run a build or tests. Report the changed files and stop for approval.

### Step 3 - Replace the authenticated identity controls with the account dropdown

Update `CarteDeBucate.Web/Views/Shared/_Layout.cshtml`:

- remove the top-level Backup JSON link;
- keep URL-based recipe import unchanged;
- replace the username badge and separate Logout item with one accessible account-menu trigger;
- show the current username in the trigger/menu;
- link Settings to `SettingsController.Index`;
- submit Log out to the existing `AccountController.Logout` POST action;
- retain anti-forgery generation through the Razor form tag helper;
- use the already bundled Bootstrap dropdown behavior.

At this step, verify by inspection that signed-out/public markup remains unaffected.

Do not run a build or tests. Report the changed files and stop for approval.

### Step 4 - Move the JSON backup interface into Data & Backup

Move the form presentation from `CarteDeBucate.Web/Views/RecipeBackups/Index.cshtml` into the Settings page's Data & Backup section:

- point Export explicitly to `RecipeBackupsController.Export`;
- point Import explicitly to `RecipeBackupsController.Import`;
- retain POST methods and anti-forgery tokens;
- retain `multipart/form-data` for Import;
- retain the `backupFile` name, JSON accept filter, required input, labels, descriptions, and separate actions;
- adapt only layout and copy needed to make the forms read naturally inside Settings.

Do not change the backup service or JSON logic.

Do not run a build or tests. Report the changed files and stop for approval.

### Step 5 - Route backup outcomes back to Settings and retire the duplicate page

Update `RecipeBackupsController` only where navigation destinations are affected:

- make the GET `Index` action redirect to `SettingsController.Index` for compatibility;
- redirect export failures to Settings;
- redirect missing-file, successful-import, and failed-import outcomes to Settings;
- preserve all current service calls, branches, logging, messages, file construction, and exception behavior.

Remove `CarteDeBucate.Web/Views/RecipeBackups/Index.cshtml` after the compatibility redirect and Settings forms are in place. Do not leave a second user-facing backup UI.

Update the focused controller tests to reflect only these redirect destinations. Do not rewrite backup behavior tests unnecessarily.

Do not run a build or tests. Report the changed files and stop for approval.

### Step 6 - Add coordinated responsive styling

Update `CarteDeBucate.Web/wwwroot/css/site.css` and, only if necessary for layout-specific encapsulation, `CarteDeBucate.Web/Views/Shared/_Layout.cshtml.css`:

- style the account trigger and dropdown with existing design tokens;
- align the dropdown safely at desktop widths;
- handle long usernames;
- keep the account menu usable inside collapsed mobile navigation;
- visually separate the three Settings sections and their rows without fighting the existing main-surface styles;
- present the placeholder states as unavailable without making them look disabled by accident;
- keep Delete account descriptive but not active or misleadingly destructive;
- preserve visible focus and sufficient touch targets.

Avoid global selectors that unintentionally alter recipe forms or other application pages.

Do not add custom JavaScript if Bootstrap already supplies the required behavior.

Do not run a build or tests. Report the changed files and stop for approval.

### Step 7 - Complete test coverage without executing it

Review and complete focused tests for:

- Settings controller authorization;
- Settings Index result;
- legacy Backup Index redirect;
- every backup non-file redirect destination;
- unchanged backup export file content and metadata;
- unchanged import service input and TempData behavior;
- unchanged Logout action behavior.

Keep `AccountControllerTests.Logout_ShouldSignOutAndRedirectToLogin` as the logout regression test unless production logout behavior actually changes. Do not add controller tests merely to restate static placeholder copy.

If the repository has no established Razor-rendering test harness, do not introduce a large new integration-test infrastructure only to inspect navigation text. Cover the account menu, exact section order, placeholder state, responsive behavior, and visual coordination through the manual verification checklist below.

Do not run the tests or a build. Report the changed files and stop for approval.

## User-Run Verification

The user will perform all verification after the implementation is complete.

### Automated commands

From the repository root, the user can run:

```bash
dotnet test CarteDeBucate.slnx
```

Running the tests before the build is acceptable because `dotnet test` builds the relevant projects by default. If the user wants a separate explicit build first, run the two commands in the opposite order.

2. Confirm the same account trigger is present on each authenticated page.

5. Confirm Settings navigates to `/Settings`.

9. Import a valid existing backup and verify the established success message appears on Settings.
