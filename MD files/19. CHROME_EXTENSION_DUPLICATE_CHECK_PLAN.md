# Plan 19 - Detectarea duplicatelor in extensia Chrome la extragere si inainte de Save

## Scop

Adauga o verificare explicita a duplicatelor dupa `SourceUrl`, astfel incat Side Panel-ul sa informeze utilizatorul imediat dupa extragere, iar editorul sa verifice URL-ul editat inainte de salvare.

Fluxul tinta este:

1. utilizatorul extrage o reteta in Side Panel;
2. daca utilizatorul este autentificat, extensia verifica imediat printr-un endpoint autentificat daca reteta exista deja;
3. daca reteta exista, extensia afiseaza mesajul `This recipe is already saved in your cookbook.` si dezactiveaza `Save to Cookbook`;
4. daca reteta nu exista, extensia activeaza Save, iar clickul trimite salvarea normala fara un al doilea GET pentru acelasi rezultat curent;
5. in editor, extensia verifica la fiecare tentativa de Save valoarea curenta din campul `Source URL`, deoarece aceasta poate fi modificata;
6. `POST /api/recipes` pastreaza verificarea existenta din Core si ramane protectia autoritativa impotriva duplicatelor si a race condition-urilor.

Verificarea se aplica ambelor suprafete care pot salva din extensie:

- Side Panel-ul principal;
- pagina separata `edit.html`, folosind `Source URL` curent din formular.

Acest plan adauga o verificare anticipata de UX in Side Panel si o verificare preflight in editor. Nu inlocuieste validarea si protectia la salvare din backend.

## Starea actuala

### Protectia existenta din Core

`RecipeLibraryService.SaveRecipe()`:

- normalizeaza `SourceUrl` prin `Trim()`;
- valideaza reteta;
- verifica existenta unei retete cu acelasi `SourceUrl`;
- foloseste `RecipeExistsBySourceUrlForUser()` cand exista un utilizator curent;
- foloseste `RecipeExistsBySourceUrl()` in context neautentificat;
- intoarce `AppTexts.RecipeAlreadyExists` si nu apeleaza `AddRecipe()` pentru duplicate.

Repository-urile JSON si SQLite compara URL-urile fara diferenta intre litere mari si mici si ignora spatiile exterioare. Verificarea per utilizator este deja implementata si testata.

Metoda care selecteaza verificarea globala sau per utilizator este in prezent privata in `RecipeLibraryService`. Contractul `IRecipeLibraryService` nu expune o interogare de existenta.

### API-ul Web existent

`RecipesApiController`:

- este protejat la nivel de controller prin JWT Bearer;
- expune numai `POST /api/recipes`;
- apeleaza `SaveRecipe()` si intoarce `400 Bad Request` cu mesajul serviciului atunci cand reteta este duplicata;
- nu ofera extensiei o verificare separata inainte de salvare.

### Extensia existenta

`recipeApiClient.js` expune numai `saveRecipeToApi()` pentru retete:

- citeste endpointul din `API_ENDPOINTS.recipes`;
- trimite JWT-ul prin headerul `Authorization: Bearer`;
- trateaza separat `401`;
- pastreaza statusul HTTP pe eroarea JavaScript;
- valideaza raspunsul JSON.

Side Panel-ul si editorul injecteaza fiecare o dependenta `saveRecipeToApi`. In prezent apasarea `Save to Cookbook` porneste direct `POST /api/recipes`.

Backend-ul respinge deja duplicatul, dar extensia afla numai din raspunsul cererii de creare.

## Contractul functional tinta

### Definitia duplicatului

O reteta este duplicata daca utilizatorul autentificat curent are deja o reteta al carei `SourceUrl` se potriveste conform regulilor existente ale repository-ului:

- spatiile exterioare sunt ignorate;
- comparatia nu tine cont de litere mari si mici;
- duplicatul altui utilizator nu este duplicat pentru utilizatorul curent.

Nu adauga detectare dupa:

- numele retetei;
- ingrediente;
- instructiuni;
- imagine;
- continut similar sau fuzzy matching.

`SourceUrl` ramane singura identitate folosita pentru aceasta verificare.

### Momentul verificarii

Momentul verificarii depinde de suprafata:

- in Side Panel, verificarea porneste imediat dupa o extragere reusita, daca autentificarea este deja confirmata;
- daca autentificarea este inca in curs de rezolvare, verificarea porneste cand aceasta se rezolva ca autentificata si reteta extrasa este inca cea curenta;
- daca utilizatorul se autentifica dupa extragere, verificarea porneste imediat dupa autentificarea reusita;
- in editor, verificarea porneste numai la apasarea `Save to Cookbook`, dupa validarea formularului.

Nu verifica:

- la simpla deschidere a Side Panel-ului fara o extragere reusita;
- la fiecare tasta introdusa in editor;
- la focus sau blur pe `Source URL`;
- prin polling.

Side Panel-ul nu porneste verificari duplicate pentru acelasi snapshot si aceeasi stare curenta. Editorul verifica fiecare snapshot valid construit la Save, deoarece URL-ul poate fi schimbat.

### Side Panel

Pentru o reteta extrasa si un utilizator autentificat:

1. dupa extragerea reusita, statusul afiseaza `Checking whether this recipe is already saved...`;
2. Save ramane disabled cat timp verificarea este in curs;
3. extensia verifica snapshot-ul format din reteta curenta si `currentRecipe.sourceUrl`;
4. daca `exists` este `true`:
   - nu apeleaza `saveRecipeToApi()`;
   - afiseaza `This recipe is already saved in your cookbook.`;
   - pastreaza reteta afisata;
   - pastreaza Edit si Print disponibile;
   - pastreaza Save disabled;
5. daca `exists` este `false`:
   - curata mesajul temporar de verificare;
   - activeaza Save;
   - clickul pe Save trimite direct `POST /api/recipes`, fara repetarea GET-ului pentru acelasi URL verificat;
6. daca verificarea tehnica esueaza cu un status diferit de `401`:
   - raporteaza eroarea;
   - marcheaza rezultatul ca necunoscut;
   - activeaza Save;
   - clickul pe Save repeta verificarea, apoi aplica politica fail-open daca aceasta esueaza din nou.

O extragere noua:

- invalideaza rezultatul verificarii anterioare;
- curata mesajul de duplicat;
- tine Save disabled pana la rezultatul verificarii noii retete, daca utilizatorul este autentificat;
- ignora orice raspuns intarziat primit pentru reteta anterioara.

Nu este necesara anularea requestului HTTP vechi, dar rezultatul sau nu are voie sa modifice reteta, statusul sau butoanele noii extrageri.

### Editor

Pentru `edit.html`:

1. formularul este validat si reteta editata este construita prin calea existenta;
2. daca formularul este invalid, nu se face nici verificarea de duplicat, nici salvarea;
3. verificarea foloseste `editedRecipe.sourceUrl`, nu URL-ul retetei extrase initial;
4. daca URL-ul este duplicat:
   - nu apeleaza `saveRecipeToApi()`;
   - afiseaza `This recipe is already saved in your cookbook.`;
   - pastreaza valorile formularului;
   - pastreaza Print si Cancel disponibile;
   - reactiveaza Save, astfel incat utilizatorul sa poata modifica `Source URL` si sa incerce din nou;
5. o noua tentativa reconstruieste reteta si verifica din nou URL-ul curent.

Reteta editata este un snapshot construit la click. Daca utilizatorul modifica formularul cat timp verificarea este in curs, secventa curenta foloseste acelasi snapshot pentru GET si eventualul POST; modificarile ulterioare intra numai intr-o tentativa noua. Nu combina date din doua stari diferite ale formularului.

Nu adauga un cache persistent al rezultatelor. Starea duplicatului din Side Panel exista numai in memoria controllerului pentru reteta curenta si se reseteaza la o extragere noua sau la pierderea autentificarii.

### Utilizator neautentificat

Comportamentul existent ramane neschimbat:

- Save este disabled;
- verificarea de duplicat nu este apelata;
- utilizatorul foloseste butonul separat `Log in`;
- autentificarea nu porneste implicit prin click pe Save.

Daca exista deja o reteta extrasa atunci cand autentificarea devine valida, verificarea porneste automat fara o noua extragere.

### Sesiune expirata

Daca endpointul de verificare intoarce `401`:

- nu se incearca `POST /api/recipes`;
- tokenul local este eliminat prin fluxul existent;
- controllerul revine in starea neautentificata;
- se afiseaza mesajul existent `Your session expired. Sign in again.`;
- zona de login reapare;
- reteta si valorile editate raman disponibile.

### Eroare tehnica la verificarea duplicatului

Pentru o eroare diferita de `401`, verificarea duplicatului este fail-open:

- eroarea este trimisa catre `reportError`;
- in Side Panel, eroarea verificarii automate nu porneste singura un POST; Save devine disponibil, iar clickul utilizatorului repeta verificarea si continua cu POST daca retry-ul esueaza non-401;
- in editor, extensia continua cu `POST /api/recipes` in cadrul aceleiasi tentative de Save;
- backend-ul ramane responsabil sa accepte reteta sau sa respinga duplicatul;
- utilizatorul nu este blocat definitiv de un endpoint auxiliar indisponibil sau de un raspuns malformat.

Daca si salvarea esueaza, se foloseste mesajul existent al salvarii.

### Race condition intre verificare si salvare

Rezultatul `exists: false` nu garanteaza ca reteta nu va deveni duplicata inainte de `POST`.

De aceea:

- verificarea existenta din `RecipeLibraryService.SaveRecipe()` nu se elimina;
- `POST /api/recipes` ramane autoritativ;
- daca o alta instanta salveaza reteta intre GET si POST, POST-ul poate respinge duplicatul;
- extensia afiseaza in continuare mesajul returnat de backend.

Nu introduce locking distribuit, rezervari de URL sau tranzactii intre GET si POST.

## Contractul API nou

Adauga endpointul autentificat:

```http
GET /api/recipes/exists?sourceUrl=<url-encoded-source-url>
Authorization: Bearer <access-token>
```

Raspuns pentru URL valid:

```json
{
  "exists": true
}
```

sau:

```json
{
  "exists": false
}
```

Contractul statusurilor:

- `200 OK` cu proprietatea booleana `exists` pentru o interogare valida;
- `400 Bad Request` pentru `sourceUrl` lipsa, gol sau care nu este URL absolut HTTP/HTTPS cu host;
- `401 Unauthorized` pentru token lipsa, invalid sau expirat.

Endpointul:

- nu intoarce reteta existenta;
- nu intoarce ID-ul, numele sau alte date ale retetei;
- nu dezvaluie datele altui utilizator;
- nu modifica date;
- mosteneste autorizarea JWT de pe `RecipesApiController`.

Foloseste mesajele existente `AppTexts.RecipeSourceUrlRequired` si `AppTexts.RecipeSourceUrlInvalid` pentru query invalid. Nu adauga texte Core duplicate pentru aceeasi validare.

## Decizii de implementare

### Expunerea verificarii prin serviciul existent

Adauga in `IRecipeLibraryService`:

```csharp
bool RecipeExistsBySourceUrl(string sourceUrl);
```

Metoda existenta privata din `RecipeLibraryService` devine publica si:

- normalizeaza valoarea primita cu `Trim()`;
- intoarce `false` pentru null, gol sau whitespace;
- foloseste `RecipeExistsBySourceUrlForUser()` cand `CurrentUserId` exista;
- foloseste `RecipeExistsBySourceUrl()` pentru contextul fara utilizator;
- nu incarca lista completa de retete;
- nu dubleaza query-ul repository-ului.

`SaveRecipe()` continua sa apeleze aceeasi metoda. Nu crea o a doua implementare a regulii de duplicat.

Actualizeaza toate implementarile de test ale `IRecipeLibraryService`, inclusiv:

- `FakeRecipeLibraryService`;
- `PipelineRecipeLibraryService` din `AuthenticationPipelineTests`.

### Actiunea API

Adauga in `RecipesApiController` o actiune `GET` pe ruta `exists`.

Actiunea:

1. normalizeaza query-ul;
2. valideaza required si URL HTTP/HTTPS;
3. nu apeleaza serviciul pentru query invalid;
4. apeleaza `RecipeExistsBySourceUrl()` o singura data;
5. intoarce numai `{ exists }`.

Nu modifica raspunsurile sau statusurile endpointului existent `POST /api/recipes`.

### Clientul JavaScript

Adauga in `API_ENDPOINTS`:

```text
recipeExists: <API_BASE_URL>/api/recipes/exists
```

Adauga in `recipeApiClient.js` functia exportata:

```text
recipeExistsBySourceUrl(sourceUrl, accessToken, fetchRequest = globalThis.fetch)
```

Functia:

- respinge lipsa tokenului cu status `401`, la fel ca salvarea;
- normalizeaza spatiile exterioare ale URL-ului;
- construieste query-ul cu `URLSearchParams` sau codare echivalenta sigura;
- foloseste metoda `GET`;
- trimite numai headerul `Authorization`;
- nu trimite body si nu adauga `Content-Type` inutil;
- trateaza `401` ca sesiune expirata;
- refoloseste citirea defensiva a raspunsului si tipul de eroare cu `status`;
- accepta numai un raspuns JSON cu `exists` boolean;
- arunca o eroare pentru raspuns `200` malformat, in loc sa considere implicit ca reteta nu exista.

Nu combina verificarea si salvarea intr-o singura functie API. Controllerul trebuie sa controleze ordinea si comportamentul fail-open.

### Dependentele controllerelor

Adauga dependenta injectata `recipeExistsBySourceUrl` in:

- `initializeSidePanelController()`;
- `initializeEditController()`.

Controllerul nu citeste direct tokenul si nu construieste URL-uri API.

`sidepanel.js` si `edit.js` compun dependenta prin:

1. `getAccessToken()`;
2. `recipeExistsBySourceUrl(sourceUrl, accessToken)`.

Aceasta pastreaza separarea actuala dintre UI, storage si fetch.

### Starea UI

In Side Panel, verificarea are loc in afara salvarii, deci adauga o stare explicita numai in memoria controllerului:

```text
duplicateCheckStatus = unknown | checking | exists | not-found
checkedSourceUrl = URL-ul normalizat asociat rezultatului curent
duplicateCheckRevision = identificator monoton pentru invalidarea raspunsurilor vechi
```

`isSaving` continua sa reprezinte numai requestul `POST`. Nu supraincarca `isSaving` pentru verificarea automata pornita dupa extragere.

In Side Panel:

- Save ramane disabled pentru `checking` si `exists`;
- Save devine enabled pentru `not-found`;
- Save poate deveni enabled pentru `unknown` dupa o eroare tehnica non-401, dar clickul repeta verificarea inainte de POST;
- Edit si Print raman disponibile in timpul verificarii, deoarece lucreaza cu acelasi snapshot deja extras;
- o extragere noua sau pierderea autentificarii incrementeaza revizia si reseteaza rezultatul;
- un raspuns poate actualiza UI-ul numai daca revizia, reteta si URL-ul sau corespund starii curente.

Tranzitia la `checking` si dezactivarea Save au loc inainte de primul `await`, astfel incat butonul sa nu devina activ pentru scurt timp intre afisarea retetei si pornirea GET-ului.

In editor, starea existenta `isSaving` acopera intreaga secventa:

```text
duplicate check -> optional POST save
```

Cat timp secventa editorului este activa:

- Save ramane disabled;
- un al doilea click nu porneste alta secventa;
- Print urmeaza regulile existente ale controllerului.

Nu persista starea duplicatului in `chrome.storage` si nu o copia in payload-ul retetei.

Mesajele statusului sunt:

```text
Checking whether this recipe is already saved...
This recipe is already saved in your cookbook.
Saving...
Recipe saved successfully.
```

Mesajul de duplicat foloseste stilul neutru existent al statusului, nu stilul verde de succes si nu stilul rosu de eroare.

Opreste-te si raporteaza rezultatele inainte de verificarea manuala.

### Pasul 11 - Checkpoint manual Web si Chrome

Utilizatorul porneste aplicatia Web si reincarca extensia unpacked.

Nu automatiza acest checkpoint fara o cerere explicita.

## Verificare manuala

### Pregatire

1. Porneste aplicatia Web pe origin-ul configurat in `apiConfig.js`.
2. In `chrome://extensions`, apasa Reload pentru extensie.
3. Autentifica extensia cu un utilizator de test.
4. Asigura-te ca exista o reteta salvata cu un URL cunoscut.

### Side Panel - duplicat

1. Deschide pagina sursa a retetei deja salvate.
2. Apasa iconita extensiei si asteapta extragerea.
3. Fara sa apesi Save, confirma ca apare `Checking whether this recipe is already saved...`.
4. Confirma ca apare `This recipe is already saved in your cookbook.`.
5. Confirma ca Save este disabled.
6. Confirma in Network ca a existat `GET /api/recipes/exists` si nu a existat un nou `POST /api/recipes`.
7. Confirma ca Edit si Print raman utilizabile.

### Side Panel - reteta noua

1. Extrage o reteta cu un URL care nu exista in Cookbook.
2. Confirma ca GET exists porneste automat dupa extragere si ca Save devine enabled dupa raspunsul `false`.
3. Apasa Save.
4. Confirma ca clickul trimite POST create fara un al doilea GET exists pentru aceeasi reteta.
5. Confirma mesajul verde de succes si Save disabled dupa salvare.
6. Apasa din nou iconita pe aceeasi pagina si confirma ca noua extragere detecteaza automat duplicatul.

### Side Panel - autentificare dupa extragere

1. Delogheaza extensia si extrage o reteta.
2. Confirma ca nu se trimite GET exists si ca Save ramane disabled.
3. Autentifica extensia fara sa extragi din nou reteta.
4. Confirma ca GET exists porneste automat pentru reteta deja afisata.
5. Confirma ca rezultatul actualizeaza corect mesajul si starea Save.

### Editor

1. Extrage o reteta si deschide Edit.
2. Introdu in `Source URL` URL-ul unei retete deja salvate.
3. Apasa Save si confirma mesajul de duplicat fara POST.
4. Confirma ca valorile formularului nu s-au schimbat.
5. Schimba `Source URL` cu un URL nou.
6. Apasa Save si confirma GET urmat de POST.
7. Confirma ca Print continua sa functioneze.

### Autentificare si erori

1. Expira sau elimina tokenul inainte de verificare si confirma revenirea la Login.
2. Simuleaza endpointul exists indisponibil la extragere si confirma ca nu porneste un POST automat, iar Save devine disponibil.
3. Apasa Save, mentine endpointul exists indisponibil, dar pastreaza POST disponibil, si confirma fallback-ul la POST.
4. Salveaza aceeasi reteta din doua contexte aproape simultan si confirma ca backend-ul respinge al doilea POST chiar daca ambele verificari initiale au intors `false`.
5. Confirma ca URL-ul cu query string este codat si verificat corect.
6. Confirma ca acelasi URL al altui utilizator nu este raportat ca duplicat.

## Edge cases obligatorii

- `sourceUrl` lipsa, gol sau whitespace.
- URL relativ.
- protocol `javascript:`, `file:` sau `ftp:`.
- URL cu query string, fragment si caractere care necesita encoding.
- diferente de litere mari/mici.
- spatii exterioare.
- acelasi URL pentru doi utilizatori diferiti.
- token lipsa, invalid sau expirat.
- raspuns `200` cu JSON malformat sau `exists` non-boolean.
- raspuns non-JSON de eroare.
- eroare de retea la verificarea duplicatului.
- clickuri Save repetate rapid.
- autentificare rezolvata dupa terminarea extragerii.
- login reusit dupa extragerea facuta ca utilizator neautentificat.
- raspuns GET intarziat dupa pornirea unei extrageri noi.
- modificarea formularului in timpul verificarii.
- duplicat creat intre GET si POST.
- reteta noua dupa un mesaj anterior de duplicat.
- extragere noua dupa un mesaj anterior de duplicat.

## Criterii finale de acceptare

- Side Panel-ul verifica automat duplicatul dupa extragere atunci cand utilizatorul este autentificat.
- Daca autentificarea devine valida dupa extragere, Side Panel-ul verifica reteta curenta fara o noua extragere.
- Un duplicat detectat in Side Panel tine Save disabled, dar pastreaza Edit si Print disponibile.
- Pentru o reteta noua verificata, Save trimite POST fara repetarea GET-ului pentru acelasi rezultat curent.
- Editorul verifica duplicatul la fiecare tentativa de Save, folosind URL-ul editat curent.
- Verificarea foloseste `SourceUrl` al retetei care urmeaza efectiv sa fie salvata.
- Un duplicat al utilizatorului curent este detectat fara un POST de creare.
- Un URL apartinand numai altui utilizator nu este raportat ca duplicat.
- Query-ul invalid primeste `400`, iar accesul neautentificat primeste `401`.
- Extensia trateaza strict raspunsul `{ exists: boolean }`.
- `401` curata autentificarea locala si afiseaza Login.
- O eroare tehnica non-401 la verificarea duplicatului nu blocheaza salvarea existenta.
- Clickurile si schimbarile de autentificare paralele nu produc verificari sau salvari paralele.
- Raspunsurile intarziate ale unei verificari vechi nu modifica UI-ul unei retete noi.
- Protectia de duplicat din `SaveRecipe()` ramane activa si autoritativa.
- Nu sunt adaugate permisiuni Chrome sau host permissions noi.
- Nu sunt modificate schema SQLite, repository-urile sau extractoarele.
- Testele C# si JavaScript acopera succesul, duplicatul, inputul invalid, autentificarea, raspunsurile malformate si race condition-ul GET-POST.
