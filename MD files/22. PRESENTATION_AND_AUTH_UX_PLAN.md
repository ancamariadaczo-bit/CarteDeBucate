# Presentation and Authentication UX Plan

## 1. Purpose

Create a welcoming public entry experience for Carte de bucate while keeping the authenticated application focused on recipe management.

The public experience consists of:

1. A presentation page at `/`
2. A login page at `/Account/Login`
3. A create-account page at `/Account/Register`

The normal authenticated application navigation must not appear on any of these pages.

This plan records the confirmed product, content, routing, authentication, localization, visual, accessibility, and acceptance requirements. The exact illustration, fonts, and decorative styling are intentionally replaceable so the visual identity can be refined later without restructuring the pages.

## 2. Confirmed Product Positioning

### Product name

**Carte de bucate**

Use this capitalization consistently in the public and authentication experience.

### Purpose

Carte de bucate is a personal recipe library for saving, importing, organizing, and finding recipes in one place.

### Target audience

Individual home cooks who collect recipes from websites, notes, photos, bookmarks, and other sources.

### Positioning statement

> Carte de bucate helps home cooks turn scattered recipes into one organized, searchable personal cookbook.

The visible website copy is Romanian; the English positioning statement above is internal product guidance.

## 3. Information Architecture and Routing

### 3.1 Public routes

Retain the application's existing MVC routes. Do not add route aliases solely for this work.

| Page | Route | Public access | Application navigation |
| --- | --- | --- | --- |
| Presentation | `/` | Yes | Hidden |
| Login | `/Account/Login` | Yes | Hidden |
| Create account | `/Account/Register` | Yes | Hidden |

### 3.2 Root-route behavior

- A signed-out visitor opening `/` sees the presentation page.
- An authenticated visitor opening `/` is redirected to `Recipes/Index`, the main recipe library.
- An authenticated visitor opening `/Account/Login` or `/Account/Register` is redirected to `Recipes/Index`.
- A signed-out visitor opening a protected route is sent to `/Account/Login` with the local return URL preserved.
- After a successful login, return the user to a valid local return URL when one exists; otherwise, redirect to `Recipes/Index`.
- After successful registration, sign the user in immediately and redirect to `Recipes/Index`.

### 3.3 Layout separation

Use explicit Razor layout separation:

- A public layout for the presentation, login, and registration pages
- The existing application layout for authenticated product pages

The public layout must not render the application's normal navigation bar or top menu. Navigation visibility must be determined by layout selection, not by checking URL strings in shared navigation markup.

## 4. Public Header

The presentation page has a public header containing:

- Text wordmark: **Carte de bucate**
- Anchor link: **Cum funcționează**
- Anchor link: **Ce poți face?**
- Anchor link: **Despre**
- Account link: **Autentificare**
- Primary account action: **Creează cont**

The first three items scroll to their corresponding presentation-page sections. `Autentificare` links to `/Account/Login`, and `Creează cont` links to `/Account/Register`.

This header is public-page navigation, not the authenticated application's navigation.

The login and registration pages should show the text wordmark linking to `/` or an equivalent clear route back to the presentation page. They must not show the presentation-page section navigation or authenticated application navigation.

**Invitation**

> Începe propria colecție de rețete

**Action**

## 6. Replaceable Visual Direction

### 6.1 Reference and initial atmosphere

The supplied `Vintage Recipe Collection Landing Page.png` is a visual reference, not the final production asset. Use its broad composition and atmosphere as an initial placeholder direction:

- Warm vintage editorial cookbook feeling
- Parchment or cream base
- Deep muted teal, warm brown, terracotta, sage, and pale peach accents
- Hero copy on the left
- Recipe- or kitchen-related imagery concentrated on the right or behind the outer hero area
- Generous negative space and strong text readability

Do not reproduce text as part of the image. All visible copy and actions must remain real HTML so they stay accessible, responsive, localizable, and independently editable.

### 6.2 Existing identity

The repository does not currently contain a reusable product logo or dedicated public-page illustration. Use:

- The text wordmark **Carte de bucate**
- Existing warm application colors as initial tokens, including the brown primary accent `#8a4f22`
- A replaceable placeholder hero asset

Do not use user-uploaded recipe photos as public brand assets.

### 6.3 Replaceability requirements

The following must be replaceable without changing page structure or business logic:

- Hero image
- Display font
- Interface font
- Color tokens
- Hero and section copy
- Decorative textures and illustrations

Keep the placeholder asset behind a stable asset path or CSS custom property. Keep typography, color, spacing, radius, and shadow choices in centralized tokens rather than distributing literal values throughout page-specific styles.

### 6.4 Image treatment

- Provide a warm gradient or solid-color fallback while the image loads or if it fails.
- Prevent the image from causing layout shift.
- Keep contrast low behind text and controls; add an overlay when necessary.
- Mark purely decorative imagery so assistive technology ignores it.
- Use responsive sizes and an efficient modern format for the eventual production asset.
- On small screens, crop, reposition, reduce, or move the visual below the copy to preserve readability.
- Do not introduce ambient animation in the placeholder version.

## 7. Authentication Scope and Account Rules

### 7.1 Supported authentication

Support the existing local account system only:

- Username and password login
- Username, password, and password confirmation registration

Do not present or imply:

- Email-based accounts
- Email verification
- Password recovery
- Magic links
- Social login
- Single sign-on

The UI must not show `Ai uitat parola?` because password recovery is not available.

### 7.2 Username requirements

- Required
- Between 3 and 30 characters
- May contain letters, numbers, spaces, periods, hyphens, and underscores
- Must be unique without regard to letter casing

Duplicate-username message:

> Acest nume de utilizator este deja folosit. Alege altul.

### 7.3 Password requirements

- Required
- Minimum 5 characters
- No mandatory uppercase, lowercase, number, or special-character composition rules
- Registration requires matching password and confirmation values
- Show the requirement before submission

Five characters is the confirmed product requirement even though a longer minimum would provide stronger security.

### 7.4 Invalid credentials

Use one generic message that does not reveal whether the username exists:

> Numele de utilizator sau parola sunt incorecte.

## 10. Localization Architecture

### 10.1 Web application

Romanian is the default and only displayed web language for this version, but the implementation must be localization-ready.

- Do not hardcode user-visible public-page or authentication text in Razor views, controllers, view models, validation attributes, or JavaScript.
- Store Romanian strings in ASP.NET Core `.resx` resource files.
- Use stable resource keys so another culture can be added without rewriting page markup or application logic.
- Include navigation, headings, body copy, buttons, field labels, validation messages, authentication errors, loading states, and accessible labels in the resource system.
- Configure the web application's default culture and fallback culture as Romanian.
- Keep localization resources organized by shared UI and page or feature where appropriate; do not place unrelated Chrome extension strings in web resources.

### 10.2 Chrome extension

The Chrome extension remains English-only in this scope, but its current public UI text must be prepared for future localization independently of the web application.

- Add and use Chrome's standard `_locales/en/messages.json` resource file.
- Move existing user-visible English strings out of extension HTML, JavaScript, and the manifest where Chrome localization supports them.
- Use `__MSG_key__` for localizable manifest values and `chrome.i18n.getMessage(...)` for runtime UI text.
- Set the appropriate manifest default locale.
- Do not add Romanian Chrome extension translations in this work.
- Preserve the extension's current English wording and behavior except where extraction requires a localization key.

## 11. Shared Visual and Interaction System

- Use one replaceable display-font token for the public wordmark and hero heading.
- Use one highly readable interface-font token for navigation, forms, buttons, and body copy.
- Use centralized type, spacing, color, radius, and shadow tokens.
- Use rounded but not excessively pill-shaped controls.
- Provide accessible hover, active, focus, disabled, loading, and error states.
- Prefer subtle borders and shadows to heavy authentication cards.
- Keep button and field heights consistent.
- Preserve strong visible keyboard focus indicators.
- Do not add a public dark theme unless the application gains a coherent product-wide dark theme.

## 12. Responsive Behavior

### Desktop

- Hero copy occupies approximately 45–55% of the available content width.
- The replaceable visual occupies the right side and may extend toward the viewport edge.
- Public navigation and account actions remain legible and visually distinct.
- Landing-page section anchors scroll to headings without hiding them beneath the header.

### Mobile

- Keep the wordmark and essential account actions accessible without awkward wrapping.
- Collapse or otherwise adapt the three section links when space is insufficient.
- Ensure the mobile navigation is keyboard- and screen-reader-accessible.
- Place hero copy before the visual.
- Crop, fade, reposition, or move the visual below the copy to preserve readability.
- Allow the primary CTA to become full-width when helpful.
- Keep the first meaningful action visible without excessive scrolling.
- Stack multi-column content in a logical reading order.

## 13. Accessibility and Quality Requirements

- Meet WCAG 2.2 AA contrast requirements for text and interactive elements.
- Make every action usable with a keyboard.
- Use a logical heading hierarchy with one page-level heading per page.
- Use appropriate semantic landmarks such as `header`, `nav`, and `main`.
- Do not render an empty `footer` landmark when the page has no footer.
- Provide visible focus states.
- Associate every form error with its field.
- Announce form-level and server errors accessibly.
- Give password visibility controls accessible names that reflect their current action.
- Respect reduced-motion preferences for scrolling or other motion.
- Support browser zoom to at least 200%.
- Set Romanian page titles and descriptions.
- Keep the page usable while the hero image loads or when it fails.
- Do not embed essential text in images.

## 14. Analytics and Privacy

Do not introduce a new analytics provider solely for this work. If analytics is already available, the following events may be tracked without including personal or credential data:

- Presentation page viewed
- Create-account action selected
- Login action selected
- Registration completed
- Login completed

Never include usernames, passwords, form contents, authentication errors, recipe contents, or other personal data in analytics payloads.

## 15. Implementation Sequence

### Phase 1: Localization and layout foundation

1. Configure Romanian web localization and create the initial resource organization.
2. Add or formalize the public Razor layout.
3. Keep the authenticated application layout unchanged except where shared localization requires an intentional update.
4. Assign the presentation, login, and registration views to the public layout.
5. Implement authenticated and unauthenticated redirects using the existing MVC routes.

### Phase 2: Presentation page

1. Build the public header and responsive navigation.
2. Build the hero with replaceable image and design tokens.
3. Add the `Cum funcționează`, `Ce poți face?`, and `Despre` sections using the confirmed resource-backed copy.
4. Add the final create-account invitation.
5. Confirm that the rejected feature strip and footer are absent.

### Phase 3: Authentication pages and validation

1. Update login and registration to use the public layout and Romanian resources.
2. Implement the confirmed username and password rules consistently in the UI and server-side validation.
3. Add password visibility controls.
4. Add accessible loading, validation, duplicate-submission prevention, and generic authentication failure states.
5. Preserve valid local return URLs and the confirmed post-authentication redirects.

### Phase 4: Chrome extension localization preparation

1. Inventory all visible English extension strings.
2. Add `_locales/en/messages.json` and the manifest default locale.
3. Replace hardcoded public UI strings with Chrome localization lookups.
4. Verify that the extension remains English-only and that behavior is unchanged.

### Phase 5: Verification

1. Run existing .NET and JavaScript tests.
2. Add or update routing, layout, validation, authentication, and localization tests.
3. Test signed-out and signed-in navigation, including direct visits to all three public routes.
4. Test mobile, tablet, desktop, large-screen, zoomed, keyboard-only, and reduced-motion behavior.
5. Test slow and failed hero-image loading.
6. Test invalid credentials, duplicate usernames, invalid username characters and lengths, short passwords, mismatched passwords, and duplicate submissions.
7. Verify that no user-visible web authentication strings remain unintentionally hardcoded or English.
8. Verify that extension UI text still appears in English through the Chrome localization system.

### Create-account page

- The page uses the public layout and does not show application or landing-section navigation.

- Protected routes continue to use the existing authentication guard and local return URL behavior.
