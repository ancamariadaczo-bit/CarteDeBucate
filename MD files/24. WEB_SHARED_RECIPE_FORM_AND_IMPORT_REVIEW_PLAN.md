# Plan 24 - Shared Web Recipe Form and Review-Before-Save Import

## Objective

Update the Web application so that adding and editing recipes use the same recipe form and importing a recipe from a URL becomes a review-before-save workflow.

The target import flow is:

1. The user enters a recipe URL and selects **Import**.
2. The application extracts the available recipe data in the background.
3. The application opens the Add Recipe form and prepopulates it with all extracted data.
4. The user reviews and, if needed, changes the imported data.
5. The recipe is persisted only when the user explicitly selects **Save**.

Importing from a URL must never save the recipe automatically.

## Scope

This plan applies only to the ASP.NET Core MVC Web application and its directly related Web tests:

- the Add Recipe flow;
- the Edit Recipe flow;
- the shared recipe form;
- the Web URL-import flow;
- deferring an imported photo until the user saves the reviewed recipe;

## Current Behavior

- `Create.cshtml` and `Edit.cshtml` already render the shared `_RecipeForm.cshtml` partial for their common recipe fields.
- The Create and Edit controller actions already use `RecipeFormViewModel`.
- `SourceUrl` and `StepsText` are nullable in `RecipeFormViewModel` and are normalized when converted to a `Recipe`.
- The URL-import POST action currently extracts a recipe, saves it immediately, optionally copies its photo, and redirects to Details.
- Because persistence happens inside the import action, the user cannot review or correct the extracted values before the first save.

## Target Form Contract

### One shared form for Add and Edit

`CarteDeBucate.Web/Views/Recipes/_RecipeForm.cshtml` remains the single source of truth for fields shared by Add Recipe and Edit Recipe.

Both flows use the same `RecipeFormViewModel` and the same field rendering, validation messages, labels, and required-field indicators. Page-specific controls may remain outside the shared partial:

- Create may contain the initial-photo control and its own Save/Cancel buttons.
- Edit may contain existing-photo management, Delete, navigation state, and its own Save/Cancel buttons.
- These page-specific controls must not duplicate the common recipe fields.

The imported recipe is mapped to `RecipeFormViewModel` and rendered through the same Create view and shared form. Do not introduce a second import-review form.

### Required and optional fields

The required fields are:

- Name;
- Ingredients.

The fields without an asterisk are optional, including:

- Source URL;
- Steps;
- Notes;
- Initial photo.

Do not append `(optional)` or equivalent text to the Source URL or Steps labels. The absence of the required-field asterisk communicates that these fields are optional.

Keep the form-level explanation that fields marked with an asterisk are required. Keep asterisks only on fields that are actually required.

An empty Source URL is valid. A non-empty Source URL must still be a valid HTTP or HTTPS URL. An empty Steps value maps to an empty step list.

The URL on the separate Import page remains required because extraction cannot start without it. This does not make Source URL required when a recipe is added or edited manually.

## Target Import Contract

### Extraction does not persist data

The `POST Import` action performs extraction only. It must not call:

- `IRecipeLibraryService.SaveRecipe`;
- `IRecipeLibraryService.UpdateRecipeAsync`;
- `IRecipePhotoUrlImporter.ImportAsync`;
- a repository or any other persistence operation.

On successful extraction, the action maps the extracted `Recipe` to `RecipeFormViewModel` and renders the Create view with the populated model.

Every value supplied by extraction must be preserved in the review form:

- recipe name;
- source URL;
- ingredients;
- steps;
- extracted image URL, when available, as transient pending-import state.

The normal Create defaults remain in effect for properties that extraction does not provide.

### Review message and missing-data feedback

The Create view must clearly tell the user that the values were imported but have not been saved and ask the user to review them before selecting Save. Use a general message such as:

> Recipe data was imported and has not been saved yet. Review the information below and make any necessary changes before saving.

Do not display a separate success message for every populated field. The populated controls already show which values were extracted, and repeating that information would add unnecessary visual noise.

When important information is missing, display one compact summary near the top of the form and a field-level message next to each affected control. The feedback depends on the field:

- **Name:** show an important missing-data message. Name remains required, and normal form validation must prevent saving until the user provides it.
- **Ingredients:** show an important missing-data message. Ingredients remain required, and normal form validation must prevent saving until the user provides at least one ingredient.
- **Steps:** show a non-blocking warning explaining that no steps were extracted. Steps remain optional, so the user may add them or save the recipe without them.
- **Source URL:** normally requires no import warning because it is populated from the URL submitted on the Import page. Show a message only if the URL unexpectedly cannot be preserved or is invalid.
- **Initial photo:** do not show a warning when no image was extracted. A photo is optional, and its absence is a normal result.
- **Notes:** do not show a missing-data message. Notes are optional and are not expected from recipe extraction.
- **Status:** do not show a missing-data message. Status uses the normal Create default and is not extracted recipe content.

For example, when ingredients and steps are missing, the summary may say:

> Some information could not be extracted:
> - Ingredients were not found. Add at least one ingredient before saving.
> - Steps were not found. You can add them now or save the recipe without steps.

Missing Name or Ingredients must be represented as validation feedback because these fields are required. Missing Steps must be represented as an import warning, not as a validation error, and must not invalidate `ModelState`.

The missing-data messages describe the current imported result only. If the user fills an affected field, normal client-side or server-side rendering must not continue to present that field as missing.

### Extraction errors

If extraction fails, remain on the Import view, preserve the entered URL, and show the extraction error. Do not open an empty Create form as though the import had succeeded.

### Deferred photo handling

An extracted image URL is transient form state; it is not part of the persistent `Recipe` model.

Add a nullable property such as `ImportedImageUrl` to `RecipeFormViewModel`. It must:

- be populated only from a successful extraction result;
- be carried by the Create form until submission;
- be validated as an HTTP or HTTPS URL when non-empty;
- never be trusted as already validated merely because it came from a hidden field;
- not be used by Edit;
- not be written into the `Recipes` table.

The Create POST action saves the reviewed recipe first. Only after recipe persistence succeeds may it call `IRecipePhotoUrlImporter.ImportAsync` for the pending imported image.

If the user selects a local initial photo while an imported image URL is also present, the local upload takes precedence and the imported image is not copied. This avoids silently adding two initial photos.

If recipe saving fails, no imported image is downloaded or persisted. If recipe saving succeeds but photo import fails, keep the saved recipe and show the existing controlled photo warning.

### Save behavior

Selecting Save from the prepopulated Add Recipe form follows the normal Create POST path:

1. MVC validates the reviewed form.
2. The controller converts the form model to a `Recipe`.
3. The recipe library service performs normal validation, ownership assignment, duplicate checking, and persistence.
4. The optional initial photo or deferred imported image is processed only after the recipe has been saved.
5. The user is redirected using the normal successful Create behavior.

The imported Source URL participates in the same duplicate protection as a manually entered Source URL. Extraction does not reserve the URL and does not bypass duplicate validation at save time.

## Acceptance Criteria

1. Add Recipe and Edit Recipe render all common recipe fields from the same `_RecipeForm.cshtml` partial and use `RecipeFormViewModel`.
2. Importing a valid URL prepopulates the Add Recipe form with every extracted recipe value.
3. No recipe is added to the database when extraction finishes or when the review form is displayed.
4. No imported photo is downloaded or persisted before the user saves the reviewed recipe.
5. The review page clearly states that the imported recipe has not yet been saved.
6. The user can edit any imported field before saving.
7. Selecting Save persists the values currently present in the form, not an earlier extraction snapshot.
8. Cancelling or navigating away from the review form leaves no imported recipe or photo behind.
9. Source URL and Steps are optional in both Add and Edit.
10. Source URL and Steps have no asterisk and no `(optional)` label text.
11. Name and Ingredients remain required and keep their asterisks.
12. A non-empty invalid Source URL is rejected, while an empty Source URL is accepted.
13. Missing steps may produce a review warning but do not block saving.
14. Import extraction failures remain on the Import page with the entered URL and an error message.
15. Missing Name or Ingredients are identified in the review summary and next to their fields, and normal validation prevents saving until they are completed.
16. Successfully populated fields do not receive repetitive per-field success messages.
17. A missing photo, Notes, or extracted Status does not produce a warning.
18. Source URL produces import feedback only if it unexpectedly cannot be preserved or is invalid.
19. Missing-data feedback is no longer shown for a field after the user provides a valid value and the form is rendered again.
20. The agent does not run a build or any tests after implementation; the user performs verification manually.
