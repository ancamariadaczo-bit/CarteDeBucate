# Plan 15 - Stabilizarea autentificarii extensiei Chrome

## Scop

Finalizeaza si stabilizeaza modificarile locale deja incepute pentru autentificarea extensiei Chrome, astfel incat:

- orice utilizator sa poata extrage, edita si printa o reteta fara autentificare;
- numai un utilizator autentificat sa poata salva o reteta in cookbook;
- autentificarea sa continue in service worker chiar daca action popup-ul se inchide cand pierde focusul;
- codul temporar primit prin callback-ul Chrome sa fie schimbat o singura data intr-un JWT;
- JWT-ul sa fie salvat in `chrome.storage.local` si reutilizat la redeschiderea popup-ului;
- API-ul de retete sa salveze reteta pentru userul identificat de JWT;
- o eroare de autentificare sau de retea sa nu dezactiveze functiile publice ale extensiei;
- configurarea pentru local si productie sa nu fie duplicata in mai multe fisiere;
- codurile temporare expirate sa nu ramana permanent in memorie;
- noile contracte de autentificare sa fie acoperite de teste automate.

Planul porneste de la modificarile locale existente. Agentul nu le revine si nu rescrie flow-ul de la zero.

## Contract functional obligatoriu

### Utilizator neautentificat

La deschiderea popup-ului:

- `Extract Recipe` este disponibil;
- zona de autentificare nu este afisata inainte de extragerea unei retete;
- lipsa serverului Web nu impiedica initializarea popup-ului.

Dupa o extragere reusita:

- `Edit Recipe` este vizibil si activ;
- `Print / Save PDF` este vizibil si activ;
- `Save to Cookbook` este vizibil, dar disabled;
- mesajul `Sign in to save recipes.` si butoanele de autentificare sunt vizibile.

### Utilizator autentificat

La deschiderea popup-ului:

- extensia citeste JWT-ul din `chrome.storage.local`;
- daca `/api/authentication/me` confirma tokenul, userul este considerat autentificat;
- zona de autentificare ramane ascunsa.

Dupa o extragere reusita:

- `Edit Recipe`, `Print / Save PDF` si `Save to Cookbook` sunt vizibile si active;
- salvarea trimite `Authorization: Bearer <token>`;
- API-ul salveaza reteta cu `UserId` din claim-ul `NameIdentifier`.

### Token invalid sau server indisponibil

- un raspuns `401` de la `/me` elimina tokenul invalid;
- o eroare tranzitorie de retea, CORS sau server nu sterge automat tokenul;
- indiferent de eroare, popup-ul este initializat si functia de extract ramane utilizabila;
- o eroare de login este raportata vizibil utilizatorului, nu numai in consola.

### Flow-ul de login

Flow-ul tinta este:

```text
popup
  -> mesaj LOGIN catre service worker
  -> un singur chrome.identity.launchWebAuthFlow
  -> Account/Login cu returnUrl local
  -> cookie MVC
  -> /api/authentication/extension-complete
  -> cod temporar single-use
  -> chromiumapp.org/authentication-callback?code=...
  -> POST /api/authentication/exchange-code
  -> JWT
  -> chrome.storage.local
```

JWT-ul nu este pus direct in callback URL.

## In afara scopului

### Butonul `Create account`

Butonul `Create account` ramane exact in starea actuala pentru moment.

In acest plan:

- nu se elimina;
- nu se redenumeste;
- nu primeste event listener;
- nu se implementeaza flow de register din extensie;
- nu se modifica `AccountController.Register`;
- nu se adauga teste pentru comportamentul lui.

Prezenta lui fara comportament este o exceptie acceptata explicit de utilizator.

### Alte excluderi

- nu se adauga refresh token;
- nu se implementeaza logout din extensie;
- nu se implementeaza revocarea server-side a JWT-urilor;
- nu se schimba durata JWT-ului fara o decizie separata;
- nu se schimba mecanismul cookie MVC existent;
- nu se schimba functionalitatile de extract, edit sau print in afara starilor UI descrise;
- nu se adauga framework JavaScript nou;
- nu se schimba runner-ul `node:test` si nu se adauga alte dependente npm.

## Decizii tehnice

1. Loginul ramane orchestrat de service worker, nu de action popup.
2. Extensia foloseste un cod temporar criptografic, single-use, cu expirare scurta.
3. Endpointul `exchange-code` ramane anonim deoarece acel cod este credentialul temporar.
4. Endpointurile protejate specifica explicit schema JWT.
5. Valorile non-secrete de configurare pot sta in `appsettings.json`; cheia JWT ramane in User Secrets local si in variabila de mediu din productie.
6. Toate URL-urile extensiei provin din `config/apiConfig.js`.
7. `API_BASE_URL` ramane singurul punct care trebuie schimbat intre pachetul local si cel de productie. Nu se introduce detectie automata fragila a mediului.
8. Pentru productie, valoarea tinta este `https://cartedebucate.onrender.com`; pentru dezvoltare locala este `https://localhost:7080`.
9. Claim-ul care contine username-ul se numeste `ClaimTypes.Name`, nu `ClaimTypes.Email`.
10. Codurile temporare expirate sunt curatate oportunist la crearea unui cod nou, fara timer de background.

1. ruleaza testele JavaScript;
2. ruleaza testele .NET relevante;
3. porneste Web-ul local;
4. reincarca extensia din `chrome://extensions`;
5. deschide popup-ul fara token si confirma ca numai Extract este disponibil initial;
6. extrage o reteta anonim si confirma Edit/Print active, Save disabled si auth prompt vizibil;
7. opreste Web-ul si confirma ca un token existent nu face popup-ul inutilizabil;
8. porneste Web-ul si executa loginul din extensie;
9. confirma o singura fereastra MVC;
10. confirma inchiderea ferestrei MVC la callback;
11. redeschide popup-ul si confirma ca userul este autentificat;
12. extrage si salveaza o reteta;
13. confirma in Web ca reteta apartine userului autentificat;
14. asteapta sau simuleaza un token invalid si confirma revenirea controlata la starea anonima;
15. verifica manual configuratia Render inainte de deploy;
16. genereaza un ZIP nou numai prin workflow-ul de release deja acceptat.

Agentul asteapta rezultatele utilizatorului si nu repara automat problemele raportate. Fiecare defect nou devine un pas separat aprobat explicit.

## Criterii finale de acceptare

Planul este complet numai cand:

- functiile Extract, Edit si Print nu depind de disponibilitatea autentificarii;
- Save este imposibil fara token si functional cu token valid;
- exista exact un singur `launchWebAuthFlow` pentru fiecare click Login;
- flow-ul continua dupa inchiderea action popup-ului;
- tokenul este salvat si reutilizat;
- `401` elimina tokenul invalid;
- erorile tranzitorii nu sterg tokenul si nu blocheaza popup-ul;
- erorile de login sunt vizibile;
- auth prompt-ul apare numai dupa extract pentru userul anonim;
- codul temporar este single-use, expira si nu produce acumulare nelimitata;
- requesturile invalide de exchange nu produc HTTP 500;
- JWT-ul foloseste semantic username, nu email;
- endpointul redundant cookie-to-JWT nu mai exista;
- toate URL-urile extensiei sunt centralizate;
- configurarea non-secreta de productie exista, iar secretul JWT este documentat extern;
- testele existente sunt adaptate si noile teste acopera flow-ul;
- autorizarea reala a API-ului este verificata prin pipeline sau ramane documentata explicit ca verificare manuala daca dependenta de integrare nu este aprobata;
- butonul `Create account` a ramas neschimbat, conform exceptiei cerute;
- utilizatorul a aprobat fiecare pas separat.
